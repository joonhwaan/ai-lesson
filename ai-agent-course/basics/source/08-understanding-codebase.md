코딩 에이전트
코드베이스 이해하기
소프트웨어 엔지니어의 가장 중요한 일 가운데 하나는 코드베이스에 대한 정신적 지도를 만들고, 시스템이 어떻게 동작하는지 깊이 이해하는 것입니다. 프로젝트가 커질수록 원하는 코드를 찾는 일은 점점 더 어려워집니다.

예전에는 큰 코드베이스를 살펴보려면 정규식을 외우거나, 효과적으로 검색하기 위한 전용 도구를 배워야 했습니다. 이제는 코딩 에이전트를 사용해 자연어로 찾고 싶은 내용을 설명하고, 에이전트가 도구를 사용해 대신 찾아보게 할 수 있습니다.

Cursor는 에이전트가 효과적으로 검색할 수 있도록 전용 도구를 제공하며, 이 도구들이 어떻게 동작하는지 이해하면 더 좋은 질문을 하고 더 정확한 결과를 얻을 수 있습니다.

에이전트 기반 검색
코드 조각을 가장 정확하게 찾는 방법은 함수 이름, 변수 이름, 기타 코드 일부 등 정확히 일치하는 문자열을 찾는 것입니다.

에이전트는 정확한 문자열을 찾는 도구인 grep을 사용할 수 있고, 더 복잡한 정규식 패턴이나 단어 경계 매치도 만들 수 있습니다. 또한 재귀적으로 검색을 수행할 수 있게 해 주는 ripgrep처럼 grep을 개선한 도구들도 있습니다.

이 두 도구 모두 매우 유용합니다. 하지만 Cursor는 Instant Grep을 통해 grep을 한 단계 더 개선하여, 대형 코드베이스에서 에이전트 기반 검색을 수행할 때 ripgrep보다 훨씬 빠르게 검색할 수 있게 했습니다.

이 도구들을 사용하기 위해 별도의 설정을 하거나 사용 방식을 바꿀 필요는 없습니다. Cursor가 자동으로 제공하며, 에이전트와 대화할 때 내부적으로 이를 사용합니다.

시맨틱 검색
정확히 무엇을 찾아야 할지 모를 때, 시맨틱 검색은 코드의 의미를 기준으로 코드베이스의 일부를 찾도록 도와줍니다. 에이전트에게 "where do we handle authentication?"이라고 물으면, 해당 파일에 "authentication"이라는 단어가 문자 그대로 들어 있지 않아도 시맨틱 검색은 middleware/session.ts 같은 파일을 찾아낼 수 있습니다.

이것이 가능한 이유는 Cursor가 커스텀 임베딩 모델로 코드베이스를 검색 가능한 벡터로 변환하기 때문입니다. 쉽게 말해, Cursor가 코드 심볼에 대한 이해를 구축하고 이를 자연어에 매핑한다는 뜻입니다.

Cursor의 시맨틱 검색에 대한 연구에 따르면, 시맨틱 검색과 grep을 함께 사용했을 때 코드베이스 관련 질문에 대한 답변 정확도가 grep만 사용할 때보다 12.5% 높았습니다. 이 향상 효과는 파일이 1,000개 이상인 대형 코드베이스에서 가장 크게 나타납니다.

이를 위해 별도로 설정할 것은 없습니다. Cursor는 애플리케이션을 시작하면 백그라운드에서 자동으로 코드베이스를 인덱싱합니다.

왜 Cursor는 에이전트에게 grep과 시맨틱 검색을 모두 제공하나요?


상관없습니다. 시맨틱 검색만으로도 모든 것을 처리할 수 있습니다.

각 도구의 강점이 다릅니다. grep은 정확한 텍스트를, 시맨틱 검색은 개념을 찾습니다. 함께 쓰면 더 넓은 범위를 다룰 수 있습니다.

어떤 검색 도구를 실행할지 사용자가 수동으로 선택할 수 있도록 하기 위해서입니다.

좋은 질문 하기
질문을 어떻게 표현하느냐에 따라 에이전트가 어떤 검색 도구를 사용하는지, 그리고 결과가 얼마나 효과적인지 달라집니다. 이는 구체적인 것에서 넓은 것까지 이어지는 스펙트럼이라고 볼 수 있습니다. 예를 들어 함수 이름처럼 정확한 텍스트 일치를 요청하는 것에서 시작해, "우리 애플리케이션에서 사용자가 결제를 제출할 때 어떤 일이 발생하는지 이해할 수 있도록 도와줘"처럼 훨씬 더 넓은 범위의 검색까지 확장될 수 있습니다.

무엇을 찾는지 알고 있을 때는 구체적으로 시작하세요. 익숙하지 않은 영역을 탐색할 때는 범위를 넓게 가져가세요. 몇 가지 예시를 살펴보겠습니다.

첫 번째 예시에서는 프롬프트가 구체적인 내용을 요구하기 때문에 에이전트가 grep부터 시작합니다. import.*PaymentService를 검색해 서비스를 참조하는 모든 파일을 찾습니다.

Ask mode example: 정밀 검색
Find all files that import from our PaymentService and show me how they handle the PaymentFailedError.

See Cursor's response
익숙하지 않은 영역을 탐색할 때는 범위를 더 넓게 가져가세요. 다음 예시에서는 애플리케이션이 결제 실패를 어떻게 처리하는지에 대해 일반적인 질문을 하고 있습니다. 첫 번째 도구 호출이 "Search codebase"인 것을 볼 수 있습니다. 이는 에이전트가 의미 기반 검색(semantic search)을 사용해 관련 파일을 찾은 뒤, 세부 내용을 채우기 위해 grep을 이어서 사용하는 것입니다.

Explore 서브에이전트
에이전트는 작업을 더 효율적으로 처리하기 위해 서브에이전트를 생성해 실행할 수 있습니다. 코드베이스를 검색하는 데 도움이 되는 기본 제공 Explore 서브에이전트가 있습니다. Explore 서브에이전트는 부모 에이전트와는 별도의 컨텍스트 윈도우에서 더 빠른 모델을 사용해 실행되므로, 본 대화를 지나치게 부풀리지 않고도 많은 병렬 검색을 수행할 수 있습니다.

이 기능을 수동으로 호출할 필요는 없습니다. 에이전트가 필요하다고 판단할 때 자동으로 사용합니다. 다만, 원한다면 서브에이전트를 직접 사용해 달라고 요청할 수도 있습니다.

기초 과정에서 이야기했듯이, 컨텍스트 사용량을 이해하고 모니터링하는 것은 중요합니다. 코드베이스에서 많은 파일을 검색하면 컨텍스트를 많이 소모하게 됩니다. 서브에이전트는 발견한 결과만 반환해 메인 대화의 초점을 유지하면서 컨텍스트 관리를 크게 개선할 수 있습니다.

아키텍처 다이어그램
규모가 크거나 익숙하지 않은 코드베이스의 경우, 코드베이스를 시각화하는 데 도움이 되는 Mermaid 다이어그램과 같은 아키텍처 다이어그램을 생성하도록 에이전트에게 요청할 수 있습니다.

Ask mode example: 아키텍처 다이어그램
체크아웃 폼, API 라우트, 결제 서비스, Stripe 통합을 포함해 우리 결제 시스템의 데이터 흐름을 보여주는 Mermaid 다이어그램을 만들어줘.

See Cursor's response
이러한 다이어그램은 온보딩, 문서화, 디자인 리뷰에 유용합니다. 또한 다른 서비스에 과도하게 의존하는 서비스나, 의도치 않은 경로로 흐르는 데이터 플로우 같은 아키텍처 문제를 드러낼 수도 있습니다.

흔한 실패 패턴: 이해하기 전에 먼저 바꾸기
자주 발생하는 실수는, 기존 코드를 충분히 이해하지 않은 채 에이전트에게 변경을 요청하는 것입니다. 이미 있는 유틸리티 함수를 새로 만들게 하거나, 코드베이스의 나머지 부분과 다른 패턴을 쓰게 만들 수 있습니다.

변경을 요청하기 전에, 먼저 에이전트에게 코드를 탐색하게 하세요:

Ask mode example: 변경 전에 탐색하기
아무 변경도 하기 전에, 지금 우리 폼 검증이 어떻게 동작하는지 보여줘. 어떤 패턴을 쓰고 있고, 공용 검증기는 어디에 있는지 알려줘.

See Cursor's response
코딩 에이전트는 요청을 문자 그대로 받아들입니다. 의도를 구체적으로 밝히지 않은 부분은 에이전트가 스스로 판단합니다. 그게 잘 먹힐 때도 있지만, 기존 패턴을 따라야 하는 변경이라면 먼저 코드베이스를 이해하고, 무엇을 어떻게 요청할지 분명히 할수록 더 좋은 결과를 얻을 수 있습니다.
