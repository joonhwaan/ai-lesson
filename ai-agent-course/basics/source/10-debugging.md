코딩 에이전트
버그 찾기와 수정하기
코딩 에이전트가 더 많은 코드를 작성할수록 엔지니어는 그 코드를 리뷰하고 버그를 추적하는 데 더 많은 시간을 쓰게 됩니다. 코딩 에이전트의 도움을 받더라도, 효과적인 디버깅의 기본기를 다시 되짚어 보고 그 과정의 일부를 에이전트에 위임해 작업 속도를 높일 방법을 찾는 일은 여전히 중요합니다.

디버깅 기본기
좋은 디버깅은 사람이 하든 에이전트가 하든 동일한 원칙을 따릅니다.

신뢰할 수 있는 재현을 만드세요. 버그를 재현할 수 없다면, 수정이 제대로 되었는지 검증할 수 없습니다. 문제를 일으키는 정확한 단계, 입력, 조건을 모두 기록하세요.
최소 재현 사례로 줄이세요. 버그와 관련 없는 것들은 모두 제거합니다. 재현 사례가 작을수록 근본 원인을 찾기 쉽습니다.
변수를 분리하세요. 한 번에 한 가지만 변경합니다. 세 가지를 바꿨는데 버그가 사라지면, 어떤 변경이 문제를 고친 건지 알 수 없습니다.
구체적인 가설을 세우세요. 근본 원인이 될 수 있는 가능성을 몇 가지 세워 봅니다. "아마 결제 코드에 버그가 있을 것 같다"는 너무 모호합니다. "calculateTotal()이 음수 할인 값을 처리하지 못해서 버그가 발생한다"는 것은 테스트할 수 있을 만큼 충분히 구체적입니다.
코드를 계측하세요. 문제가 있다고 의심되는 부분의 입력과 출력에 로깅을 추가합니다. 기대하는 값과 실제 값을 비교하세요.
테스트로 회귀를 막으세요. 버그를 찾고 수정했다면, 그 버그를 잡아낼 수 있는 테스트를 작성합니다. 이렇게 하면 동일한 버그가 다시 돌아오는 것을 막을 수 있습니다.
디버깅의 두 가지 접근법
간단한 오류를 빠르게 해결하기
오류 메시지가 명확하거나 원인이 단순한 버그의 경우, 에이전트가 문제를 직접 찾아 수정할 수 있는 경우가 많습니다. 오류를 붙여넣고 언제 발생하는지에 대한 맥락을 조금 알려준 뒤 에이전트에 맡기면 됩니다.

Agent example: 스택 트레이스 디버깅
This test is failing:
TypeError: Cannot read properties of undefined (reading 'profile')
at getProfile (src/services/UserService.ts:45)
at UserController.show (src/controllers/UserController.ts:23)
The error happens when a user created before we added the profile onboarding flow tries to view their profile. Find the root cause and fix it.

See Cursor's response
원인이 오류 메시지에 바로 드러나는 경우에 특히 잘 동작합니다. 에이전트는 스택 트레이스를 읽고 코드를 찾은 뒤 수정합니다. 하지만 항상 통하는 것은 아니므로, 근본 원인을 찾기 위해 더 체계적인 접근이 필요할 수 있습니다.

Debug Mode: 증거 우선
더 까다로운 버그에는 Debug Mode가 다른 접근법을 사용합니다. 수정안을 추측하는 대신, 먼저 런타임 증거를 수집합니다.

에이전트 드롭다운의 Debug Mode
Debug Mode는 디버깅의 기본기를 반영하는 다섯 단계로 동작합니다:

무엇이 잘못됐을 수 있는지에 대한 가설을 세웁니다
타깃 로깅으로 코드를 계측합니다
데이터를 수집하는 동안 버그를 재현해 달라고 요청합니다
로그를 분석해 근본 원인을 식별합니다
수집된 증거를 바탕으로 정확히 겨냥한 수정을 수행합니다
Debug mode example: Debug Mode: 간헐적 실패
Checkout is failing intermittently for some users. No consistent error message. Sometimes the order goes through, sometimes it silently fails and the user sees a blank confirmation page.

See Cursor's response
Debug Mode는 가장 까다로운 버그를 찾아 수정하는 데 도움을 줍니다. 앞에서 다룬 기본기를 바탕으로 에이전트가 효과적인 디버거가 되도록 하며, 그렇지 않으면 직접 수동으로 해야 했을 조사 과정을 자동화합니다.

두 사용자가 동시에 같은 문서를 편집할 때만 나타나는 버그가 있습니다. 근본 원인을 찾는 데 더 적합한 접근법은 무엇인가요?


오류를 붙여넣고 에이전트에게 수정해 달라고 요청한다.

여러 모델을 동시에 실행
까다로운 버그의 경우, 서로 다른 모델이 서로 다른 부분을 찾아내기도 합니다. Cursor에서는 동일한 디버깅 프롬프트를 여러 모델에서 동시에 실행할 수 있습니다. 각 에이전트는 격리된 상태로 작동하므로 서로 간섭하지 않습니다.

워크플로:

재현 단계와 가설을 포함한 명확한 디버깅 요약을 작성합니다
에이전트 드롭다운에서 여러 모델을 선택합니다
프롬프트를 제출하면 각 모델이 독립적으로 작동합니다
각 모델이 제안한 수정 방법을 비교합니다
가장 강력한 근거를 가진 접근법을 선택합니다
Cursor는 어떤 해결책이 가장 좋다고 판단하는지 제안해 주지만, 최종 해결책만이 아니라 그 추론도 함께 평가해야 합니다. 수정이 정확한지 더 확인하려면, 모델에게 자신의 결과가 올바르게 작동하는지 검증하고 그것이 올바른 해결책인지 확인해 달라고 요청할 수 있습니다.

런타임 데이터를 에이전트 루프에 포함하기
에이전트는 코드만 읽어도 성능 문제와 흔한 버그를 찾아낼 수 있습니다. 하지만 더 많은 런타임 정보를 제공할수록 더 깊이 파고들 수 있습니다.

질문부터 시작하세요
조사할 때 항상 로그나 프로파일링 도구가 필요한 건 아닙니다. 에이전트에게 직접 질문하면 코드에서 흔한 문제들을 분석해 줍니다.

Agent example: 코드 기반 성능 디버깅
주문이 많은 사용자의 주문 내역 페이지가 로딩되는 데 4초가 걸립니다. 왜 이렇게 느린가요?

See Cursor's response
위 예시에서 에이전트는 코드를 훑어보며 느린 쿼리를 찾아냈습니다. 별도의 로깅이나 성능 프로파일링은 필요하지 않습니다. 일부 성능 문제는 이 정도만으로도 충분합니다.

런타임 증거를 제공하세요
코드 분석만으로는 부족할 때, 에이전트에 실제 데이터를 입력하세요. 터미널 출력, 쿼리 로그 또는 기타 데이터를 대화에 그대로 붙여 넣으면 됩니다. 에이전트는 이 데이터를 활용해 더 효과적으로 근본 원인을 찾을 수 있습니다.

예를 들어 느린 데이터베이스 쿼리를 조사 중이라면, 느린 Postgres 쿼리에 대해 EXPLAIN ANALYZE를 실행하고 출력을 붙여 넣으면, 에이전트가 문제를 스키마까지 거슬러 올라가 추적할 수 있습니다:

Agent example: EXPLAIN ANALYZE 디버깅
This query is taking 1.2 seconds in production. Here's the EXPLAIN ANALYZE output:
Seq Scan on orders  (cost=0.00..45892.00 rows=47 width=244) (actual time=0.423..1203.112 rows=47 loops=1)
Filter: (user_id = 'usr_abc123')
Rows Removed by Filter: 2341856
Planning Time: 0.089 ms
Execution Time: 1203.298 ms
Find why it's doing a sequential scan and fix it.

See Cursor's response
이와 같은 패턴은 애플리케이션 로그, 프로파일링 데이터, 빌드 및 테스트 출력에도 그대로 적용할 수 있습니다.

프런트엔드 디버깅에는 브라우저 사용하기
프런트엔드 문제 발생 시 Cursor의 integrated browser를 사용하면 에이전트가 웹 애플리케이션에 직접 접근할 수 있습니다. 사용자가 아무것도 복사할 필요 없이 콘솔 로그를 읽고, 네트워크 요청을 검사하고, DOM을 관찰할 수 있습니다.

에이전트에게 페이지를 열어 문제를 재현하고, 오류는 콘솔에서, 느린 요청은 네트워크 탭에서 확인하라고 지시하세요. 에이전트는 DevTools에서 여러분이 보게 될 것과 동일한 내용을 보고, 문제를 소스 코드까지 추적할 수 있습니다.

MCP로 모니터링 도구 연결하기
MCP 서버는 에이전트에 새로운 기능을 부여하고 운영 관측 도구와 연결해 줍니다. 데이터를 수동으로 붙여넣는 대신, 에이전트가 필요할 때마다 직접 가져옵니다.

Agent example: MCP 기반 디버깅
어제 배포 이후로 체크아웃 오류가 급증하고 있어요. Sentry에서 상세 정보를 가져오고 Datadog 로그를 확인해서 무슨 일이 벌어지고 있는지 파악해 줄 수 있나요?

See Cursor's response
위 예시에서 에이전트는 MCP를 통해 Sentry에 질의하여 관련 오류 상세 정보를 가져옵니다. 그런 다음 그 오류를 로그와 연관시키고, 문제를 일으키는 코드를 찾은 뒤, 같은 대화 안에서 수정안을 제안합니다.

디버깅에 유용한 MCP 서버:

Sentry: 오류 상세 정보, 스택 트레이스, breadcrumbs
Datadog: 운영 로그와 APM 트레이스
Databases: 운영 데이터를 쿼리해 가설을 검증
Linear 또는 GitHub Issues: 버그 리포트와 재현 단계를 대화에 가져오기
운영 애플리케이션의 모니터링 알림이 자동으로 에이전트 조사를 트리거하도록 워크플로를 설정할 수 있습니다. 오류율이 치솟으면 Linear에 티켓이 생성되고, 사람이 확인하기도 전에 에이전트가 문제 진단을 시작합니다. 이렇게 하면 고객이 보고한 오류를 해결하는 시간을 줄이거나, 심지어 고객이 알아차리기 전에 문제를 고칠 수도 있습니다.

흔한 실패 패턴: 이해하지 못한 수정안을 그대로 받아들이기
수정을 이해하지 못하면 그게 맞는지 검증할 수 없습니다. 에이전트가 null 체크를 추가해서 에러는 사라질 수 있지만, 실제 데이터 불일치는 그대로 남아 있을 수 있습니다.

에이전트가 수정안을 제안하면 이해될 때까지 질문하세요. 왜 해당 값이 null인가요? 무엇이 바뀌어서 이런 일이 발생했나요? 이게 근본 원인인가요, 아니면 증상만 가리고 있는 건가요? foundations에서 다뤘듯이, 에이전트는 그럴듯해 보이는 설명을 지어낼 수 있습니다. 에이전트가 실제 근본 원인을 찾아냈는지 확인하려면, 스스로 이해를 쌓고 조사에서 얻은 데이터를 활용해야 합니다.
