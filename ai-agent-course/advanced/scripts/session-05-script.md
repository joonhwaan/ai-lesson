## [복습 · 5분] 개념에서 구현으로

🎙️ 시작 전에 한 문장만 챙겨갈게요. 세션 04에서 우리는 RAG를 "외부 장기기억을 선택적으로 회상하는 메커니즘"이라고 봤어요. 그때 청킹이니 재랭킹이니 하이브리드 검색이니는 개념만 짚고 "구체 구현은 별도 심화로 미룬다"고 했죠. 오늘이 바로 그 별도 심화예요. 개념에서 구현으로 내려가는 시간이에요.

오늘 머리에 박고 갈 한 문장은 이거예요. 화면 보세요. RAG의 품질은 "생성"이 아니라 대부분 "검색"에서 결정된다. LLM은 받은 청크를 충실히 요약할 뿐이에요. 잘못된 청크를 받으면 그럴듯하게 틀려요. 그래서 오늘 절반은 "어떻게 잘 검색되게 짓는가"에 쓸 거예요.

💬 예상 질문 — "세션 04에서 RAG 했는데 또 해요?" 04는 RAG가 뭔지, 왜 메모리의 한 형태인지였고요. 05는 그걸 실제로 어떻게 만드느냐예요. 같은 단어지만 추상화 층이 한 단계 내려가요.

## [개념 강의 ① · 20분] 색인 파이프라인 — 청킹·임베딩·벡터DB

🎙️ 화면의 색인 파이프라인 그림을 같이 봐요. 왼쪽이 오프라인 색인 단계예요. 문서를 청크로 자르고, 임베딩으로 벡터를 만들고, 벡터DB에 저장해요. 오른쪽이 온라인 질의 단계고요. 질문이 들어오면 같은 임베딩으로 벡터를 만들어서, top-k로 검색하고, 재랭킹하고, 프롬프트에 주입해서 LLM이 생성해요.

먼저 청킹이에요. 핵심은 이거예요. 검색의 단위는 문서가 아니라 청크다. 청킹이 검색 품질의 첫 단추예요. 너무 작게 자르면 맥락이 잘려서, 검색은 정확한데 답에 필요한 정보가 흩어져요. 너무 크게 자르면 한 청크에 잡음이 섞여서 임베딩이 뭉개지고 엉뚱한 게 끌려와요. 실무 출발점은 512에서 1024 토큰에 10에서 20% 오버랩, 그다음 평가로 튜닝이에요.

💬 예상 질문 — "오버랩은 왜 줘요?" 경계에서 문장이 잘리면 그 문장이 어느 청크에도 온전히 안 들어가요. 살짝 겹쳐 주면 경계 정보가 양쪽에 다 남아요.

🎙️ 그리고 청크마다 메타데이터, 출처랑 페이지랑 날짜를 꼭 붙여 두세요. 나중에 인용할 때랑 "2024년 이후 문서만" 같은 필터링에 써요. 세션 04 demo-task-spec의 cite 도구가 여기서 살아나요.

🎙️ 다음은 임베딩이에요. 텍스트를 의미를 담은 고차원 벡터로 바꾸는 거예요. 의미가 가까우면 벡터 거리가 가까워요. 화면 예시 보시면 "고양이가 야옹"이랑 "냐옹거리는 새끼 고양이"는 벡터가 가깝고, "주식 시장 폭락"은 멀어요. 여기서 제일 중요한 경고 하나. 화면 경고 박스요. 색인할 때랑 질의할 때 다른 임베딩 모델을 쓰면 벡터 공간이 어긋나서 검색이 통째로 망가져요. 색인이랑 질의는 반드시 같은 모델, 같은 전처리예요.

🎙️ 마지막으로 벡터DB랑 ANN이에요. 수백만 벡터에서 가까운 걸 다 비교하면 느려요. 그래서 근사 최근접 이웃, ANN을 써요. Flat은 전수 비교라 정확하지만 느리고, IVF는 군집으로 나눠 일부만 보고, HNSW는 다층 그래프로 빠르고 정확하지만 메모리를 더 써요. ANN은 결국 정확도랑 속도의 손잡이예요. 넓게 탐색하면 정확하고 느리고, 좁게 하면 빠르고 놓쳐요. 여기서 꼭 짚을 게, 정답이 검색 후보에 아예 없으면 뒤에서 아무리 재랭킹해도 못 살려요.

## [개념 강의 ② · 20분] 검색 품질의 세 손잡이 + 평가

🎙️ 검색 품질을 좌우하는 손잡이가 넷이에요. top-k, 재랭킹, 하이브리드, 그리고 메타데이터 필터링.

top-k는 몇 개를 끌어올까예요. 작으면 잡음은 적은데 맥락이 부족하고, 크면 안 놓치는데 잡음이랑 비용이 늘어요. 보통 재랭킹 전에는 넉넉히 20에서 50개 가져오고, 재랭킹 후에 프롬프트엔 3에서 6개만 넣어요.

재랭킹이 두 번째예요. 1차로 빠른 벡터 검색으로 후보를 많이 가져온 다음, cross-encoder 같은 정밀 모델로 질문이랑 청크 짝을 다시 채점해서 상위만 남겨요. 쉽게 말하면 1차 검색은 recall, 놓치지 않기를 맡고, 재랭킹은 precision, 엉뚱한 거 걸러내기를 맡아요. 역할 분담이 핵심이에요.

세 번째가 하이브리드예요. 키워드 검색 BM25랑 벡터 검색을 결합해요. 화면 표 보시면, "에러코드 E1042" 같은 고유명사는 키워드가 강하고, "결제가 자꾸 실패해요" 같은 건 벡터가 강해요. 그래서 둘을 섞으면 제일 좋아요. 점수를 가중합하거나 RRF로 순위를 융합해요.

🎙️ 네 번째가 메타데이터 필터링이에요. 벡터 검색은 "의미가 가까운가"만 보는데, 실무 질문엔 조건이 붙잖아요. "2024년 이후 문서에서", "정책 문서만", "내가 볼 권한 있는 것만" 이렇게요. 그래서 색인할 때 청크에 붙여둔 메타데이터, 날짜나 문서종류나 권한 같은 걸로 검색 범위를 좁혀요. 여기서 한 가지 감각만 챙기면, 필터를 먼저 걸지 검색을 먼저 할지가 갈려요. 필터가 후보를 많이 걷어내면, 예를 들어 한 사용자 문서만 보면, 필터를 먼저 거는 pre-filtering이 유리해요. 검색부터 하면 top-k를 거의 다 버리고 빈손이 되거든요.

💬 예상 질문 — "권한 없는 문서 못 보게 하려면 프롬프트에 '남의 문서 쓰지 마'라고 쓰면 되나요?" 안 돼요. 그건 인젝션으로 우회돼요. 멀티테넌시 보안은 검색 필터로 강제해야 해요. tenant랑 acl을 필터에 넣어서, 권한 없는 청크는 애초에 검색 결과에 안 끼게요. 모델 눈에 안 들어오면 샐 수가 없죠. 권한 없는 데이터는 컨텍스트에 아예 넣지 않는다, 이게 원칙이에요.

💬 예상 질문 — "그냥 벡터만 쓰면 안 돼요?" 동의어나 의역은 벡터가 잘 잡는데, 정확한 코드나 희귀한 고유명사는 벡터가 의외로 약해요. 그래서 키워드를 같이 둬요.

🎙️ 이제 평가예요. 이게 오늘의 클라이맥스예요. RAG는 두 군데서 실패해요. 검색에서 관련 청크를 못 찾거나, 생성에서 근거를 무시하고 창작하거나. 화면 표처럼 나눠서 측정해요. 검색은 Recall@k나 MRR로 "정답 청크가 top-k 안에 있었나"를 보고, 생성은 faithfulness로 "답이 검색된 근거에만 기반하나"를 봐요. 핵심 메시지는 이거예요. 검색이 틀리면 생성은 절대 맞을 수 없다. "답이 이상하다"의 80%는 검색 문제예요. 그래서 검색 지표를 먼저 봐요. 이 faithfulness 지표는 세션 09 평가에서 에이전트 전체 평가로 다시 나와요.

## [개념 강의 ③ · 20분] Agentic RAG

🎙️ 지금까지는 질문 하나에 검색 한 번, 고정 파이프라인이었어요. 그런데 세션 01에서 03까지 배운 에이전트의 본질이 뭐였죠? 동적 제어였어요. 검색 자체를 에이전트 결정에 맡기면 한 단계 강해져요. 이게 Agentic RAG예요.

첫째, 검색할지 말지를 결정해요. "2 더하기 2는?"에 벡터DB를 뒤질 이유가 없잖아요. 에이전트가 retrieve 도구를 부를지 말지를 스스로 골라요. 세션 02의 function calling 그대로예요. 도구가 retriever일 뿐이에요.

둘째, 쿼리 재작성이에요. 사용자 질문은 검색에 나쁜 형태일 때가 많아요. 대명사 쓰고 맥락에 의존하고요. 화면 예시처럼 "그거 작년 것도 돼?"를 "2023년 환불 정책 적용 범위"로 에이전트가 먼저 다시 써요.

셋째, 다단계 검색이랑 self-RAG, corrective RAG예요. 화면 그래프 보세요. 검색 결과를 에이전트가 비평해요. 근거가 충분하면 생성하고, 부족하면 쿼리를 고치거나 소스를 바꿔서 다시 검색해요. 생성한 다음에도 답이 근거에 기반하는지 한 번 더 확인하고, 아니면 되돌아가요. self-RAG는 모델이 "검색이 필요한가, 이 청크가 관련 있나, 내 답이 충실한가"를 스스로 판단하는 거고, corrective RAG는 검색 품질이 낮으면 웹 검색으로 폴백하는 거예요.

🎙️ 여기서 꼭 짚을 게 있어요. 이거 새 마법 아니에요. 세션 03의 Reflection, 자기비평 루프를 검색에 적용한 거예요. 같은 패턴, 다른 무대. 이 코스 내내 나오는 메시지죠.

💬 예상 질문 — "그럼 무조건 Agentic RAG가 좋아요?" 아니에요. 루프가 돌면 LLM 호출이 늘어서 비용이랑 지연이 커져요. 단순 FAQ 검색엔 고정 RAG가 더 싸고 빨라요. 필요할 때만 동적으로 가는 거예요.

🎙️ 마지막으로 멀티 소스예요. 우리 리서치 어시스턴트는 이제 도구가 둘이에요. web_search는 외부 웹이라 최신이고 폭넓고, 내부 retriever는 사내 벡터DB라 정확하고 비공개 지식을 알아요. 에이전트가 질문에 따라 어느 소스를 쓸지 골라요. 이 "소스별 전문 에이전트" 아이디어가 세션 08 멀티 에이전트에서 RAG Research worker로 확장돼요.

## [데모·토론 · 20분] retriever 달기

🎙️ 코드 데모 파일은 따로 없어요. demos 폴더의 raw, LangChain, LangGraph 축이랑 별개로, 여기선 설계를 같이 모델링할게요. 화면 코드 보시면, retriever를 그냥 또 하나의 도구로 추가해요. 세션 02 function calling 그대로요. query를 임베딩하고, 색인이랑 같은 모델로요, ANN으로 top-k 가져오고, 재랭킹해서 소수만 반환해요. 그리고 TOOLS 딕셔너리에 web_search, calculator 옆에 retriever를 그냥 추가하면 끝이에요.

칠판에 이 시나리오를 그려 주세요. 사용자가 "우리 환불 정책상 이 주문 환불되나?"라고 물어요. 에이전트가 retriever를 호출해서 정책 청크 다섯 개를 회수하고, 근거가 충분한지 보고, 부족하면 쿼리를 고쳐 재검색하고, 충분하면 인용과 함께 답해요. demo-task-spec의 cite가 출처를 달아 주죠.

🎙️ 토론은 화면 질문 다섯 개로 가요. 특히 3번, "답이 그럴듯한데 출처를 확인하니 근거가 없다"는 환각을 검색 지표로 잡을지 생성 지표로 잡을지, 평가 셋을 어떻게 설계할지를 꼭 같이 이야기해 보세요. 오늘의 핵심이 거기 다 들어 있어요.

🎙️ 오늘 정리하면, 색인 파이프라인은 청킹에서 임베딩에서 벡터DB, 검색 품질은 top-k랑 재랭킹이랑 하이브리드, 평가는 검색이랑 생성을 나눠서, 그리고 Agentic RAG로 검색을 에이전트가 운용하는 것까지 봤어요. 한 문장으로, 검색이 80%고 RAG는 메모리 설계의 한 선택지를 실제로 짓는 일이에요. 다음 시간 세션 06에서는 지금까지 손으로 짠 이 모든 걸 LangChain 프레임워크 추상으로 다시 그려 볼게요. 수고하셨습니다.
