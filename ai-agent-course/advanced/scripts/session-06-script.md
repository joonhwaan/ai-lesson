## [복습 · 5분] 우리가 세션 02에서 직접 짠 것

🎙️ 자 시작 전에 한 문장만 머리에 박고 갈게요. 프레임워크는 우리가 세션 02에서 손으로 짠 루프를 "치워주는" 게 아니에요. 같은 일을 규약, 인터페이스 위에 다시 그려주는 거예요. 그러니까 추상화 뒤에 뭐가 있는지 알고 쓰자, 이게 오늘의 척추예요.

기억 되살려 볼게요. 세션 02에서 우리는 리서치 어시스턴트를 raw API만으로 만들었어요. 웹 검색에 계산기 붙여서 multi-step 추론하는 거요. 핵심은 손으로 돌린 `while` 루프였죠. 화면 의사코드 보시면, LLM을 호출하고, 응답에 도구 호출이 있으면 파싱하고, 실행하고, 결과를 메시지에 주입하고, 다시 반복. 도구 호출이 없으면 최종 답을 반환하고 끝.

이 루프에서 우리가 손으로 책임진 게 다섯 가지였어요. 첫째, LLM SDK 호출 형식. OpenAI랑 Claude 메시지 포맷이 다르잖아요. 둘째, 도구 호출 파싱. JSON 뽑고 에러 처리하고. 셋째, 도구 디스패치. 이름을 함수에 매핑하고. 넷째, 메시지 누적이랑 컨텍스트 관리. 다섯째, 출력 포맷팅. 문자열을 구조화 데이터로요.

이 다섯 가지가요, 정확히 LangChain이 추상화하려는 바로 그 지점이에요.

💬 예상 질문 — "그럼 raw는 헛수고였던 거예요?" 절대 아니에요. raw를 손으로 짜 봤기 때문에 오늘 LangChain 안에서 "아, 지금 이게 그 ④ 결과 주입 단계구나"를 읽어낼 수 있는 거예요. 그게 이 강의 철학이에요.

## [개념 강의 ① · 20분] 프레임워크가 해결하는 문제 + 핵심 추상 4종

🎙️ raw 루프를 한 번이라도 짜 본 사람은 이 통증들을 알아요. 화면 표를 같이 볼게요.

OpenAI랑 Claude 메시지 포맷이 달라서 코드가 벤더에 묶이는 통증. LangChain은 `Model` 추상으로 처방해요. `ChatOpenAI`, `ChatAnthropic`을 같은 인터페이스로요. 프롬프트가 f-string 지옥이 되는 통증은 `PromptTemplate`으로. 도구 스키마를 손으로 JSON 적는 통증은 `@tool` 데코레이터로. LLM 출력을 매번 파싱하는 통증은 `OutputParser`로. 조각들을 매번 손으로 이어붙이는 통증은 LCEL, 파이프 연산자로.

쉽게 말하면 LangChain은 "에이전트를 대신 만들어주는 마법"이 아니에요. 반복되는 접합부, 영어로 glue라고 하는데, 그 풀칠 작업을 표준 인터페이스로 흡수하는 거예요. 비유하면 이케아 가구 같은 거예요. 나사랑 판자를 직접 깎던 걸, 규격화된 부품이랑 정해진 연결 방식으로 바꿔준 거죠. 그런데 가구를 만든다는 본질은 안 변해요. 루프 자체의 본질, LLM에서 도구로 결과로 반복으로, 그건 사라지지 않아요. 누가 그 루프를 들고 있느냐만 바뀌어요.

화면 다이어그램 보시면 raw API는 모든 glue를 손으로 작성해서 유연하지만 장황하고, LangChain은 glue를 프레임워크가 표준 인터페이스로 줘서 간결하지만 블랙박스예요. 그런데 둘 다 화살표가 같은 곳을 가리키죠. "LLM에서 도구로 결과로 반복으로 답으로." 본질은 동일해요. 표현만 바뀐 거예요.

자 이제 핵심 추상 4종을 하나씩 볼게요. LangChain의 거의 모든 게 이 네 블록의 조합이에요.

첫째, Models. LLM 호출의 통일된 입구예요. 화면 코드 보시면 `ChatAnthropic`이든 `ChatOpenAI`든 만들어서 `llm.invoke`를 부르면 벤더 무관하게 같은 호출이에요. 세션 02에서 우리가 직접 if문으로 분기하던 SDK 차이를 이 Model 한 겹이 흡수해요.

둘째, Prompts. 프롬프트의 템플릿화예요. `ChatPromptTemplate.from_messages`로 system이랑 human 메시지를 정의하는데, `{question}` 같은 변수 슬롯이 명시적이죠. f-string을 여기저기 흩뿌리는 대신 재사용 가능한 객체로 만드는 거예요. 변수 자리가 명확하니까 버전관리랑 테스트가 쉬워져요.

셋째, Tools. 함수에서 스키마를 자동 생성해요. `@tool` 데코레이터를 `web_search`나 `calculator` 함수 위에 붙이면, 세션 03에서 우리가 손으로 적던 그 JSON 스키마를 시그니처랑 타입힌트랑 docstring에서 자동으로 만들어줘요. 여기서 중요한 거. docstring이 곧 도구 설명이 돼요. 그러니까 docstring 품질이 진짜 중요해요.

넷째, Output Parsers. 출력의 구조화예요. 화면 보시면 `prompt | llm | StrOutputParser()` 이렇게 해서 메시지 객체를 순수 문자열로 바꿔요. LLM의 raw 응답을 문자열이나 JSON이나 Pydantic 모델로 변환하고 검증해요. 세션 02의 "직접 파싱"이 이 블록으로 들어온 거예요.

💬 예상 질문 — "@tool이 알아서 스키마 만들어주니까 docstring은 대충 써도 되죠?" 정반대예요. LLM은 docstring을 보고 도구를 골라요. docstring이 빈약하면 도구 선택이 틀려요. 세션 03의 "도구 설명은 LLM을 위한 프롬프트다" 원칙이 여기 그대로 적용돼요.

## [개념 강의 ② · 20분] LCEL과 Runnable 인터페이스

🎙️ 자 4종 블록을 알았으니, 이제 이걸 어떻게 이어붙이느냐예요. 그 비밀이 Runnable이랑 LCEL이에요.

먼저 Runnable. LangChain의 핵심 통찰이 이거예요. 모든 컴포넌트를 같은 인터페이스로 만들면 자유롭게 조립할 수 있다. 그 인터페이스가 Runnable이에요. 화면 표 보시면 `.invoke`는 입력 하나에 출력 하나, `.batch`는 여러 입력 병렬 처리, `.stream`은 토큰 스트리밍, `.ainvoke`는 비동기 버전.

여기서 멋진 게, Model도 Prompt도 Parser도, 심지어 일반 파이썬 함수도 `RunnableLambda`로 감싸면 전부 Runnable이에요. 쉽게 말하면 다들 똑같은 모양의 콘센트를 달고 있는 거예요. 그래서 입력이랑 출력 타입만 맞으면 뭐든 끼워 연결할 수 있어요. 레고 블록처럼 돌기랑 홈 규격이 같으니까 마음대로 쌓는 거죠.

그래서 나온 게 LCEL이에요. 화면 보시면 `chain = prompt | llm | StrOutputParser()` 이렇게 파이프로 묶고, `chain.invoke`로 질문을 넣어요. 이 파이프는 유닉스 파이프랑 같은 발상이에요. 왼쪽의 출력이 오른쪽의 입력으로 흐르는 거예요. 다이어그램 보시면 question이 prompt로 들어가서 ChatPromptValue가 되고, llm으로 흘러서 AIMessage가 되고, StrParser로 흘러서 최종 문자열이 되죠.

LCEL로 짜면 공짜로 따라오는 게 있어요. 자동 배치, 스트리밍, 비동기. 체인 전체가 Runnable이니까 `.batch`, `.stream`, `.ainvoke`를 그대로 써요. 그리고 부분 실행이랑 추적. LangSmith로 각 단계 입출력을 추적할 수 있어요. 이건 세션 09 예고고요. 또 타입 검사. 단계 간 입출력 불일치를 일찍 잡아줘요.

그런데 여기 중요한 경고가 하나 있어요. 화면 경고 박스 보세요. LCEL 체인은 한 방향 파이프예요. 세션 02의 루프, 그러니까 반복이랑 조건분기는 단순 파이프로 표현이 안 돼요. 물은 위에서 아래로 한 방향으로만 흐르잖아요. 거꾸로 거슬러 올라가거나 갈림길에서 선택하는 건 파이프만으로 못 그려요. 그래서 LangChain은 에이전트 실행을 위해 `AgentExecutor`를, 또는 더 명시적인 LangGraph를 따로 둬요. 이게 세션 07으로 이어지는 다리예요.

💬 예상 질문 — "그러면 모든 걸 LCEL 파이프로 짜면 안 되는 거예요?" 직선으로 흐르는 데이터 변환이면 LCEL이 딱이에요. 그런데 우리 리서치 어시스턴트처럼 몇 번 돌지 모르고 매번 도구 쓸지 말지 결정하는 루프는 파이프로 못 그려요. 그래서 AgentExecutor가, 그리고 다음 주 LangGraph가 필요한 거예요.

## [데모 · 20분] `demos/02_langchain_agent.py` — 세션 02 루프의 재구성

🎙️ 자 이제 실제 데모예요. 세션 02랑 완전히 동일한 리서치 어시스턴트를 LangChain으로 다시 짜볼 거예요. 같은 질문, 같은 도구, 다른 표현. 도구는 `web_search`랑 `calculator`예요.

먼저 도구 정의. 화면 보시면 `@tool` 붙인 `web_search`랑 `calculator`가 있고, docstring으로 "웹 검색 결과 상위 N개 스니펫을 반환한다", "산술식을 평가한다" 적혀 있죠. 세션 03에서 우리가 손으로 짜던 그 JSON 스키마가 여기서 사라졌어요. 데코레이터가 다 만들어준 거예요.

다음은 모델 더하기 프롬프트 더하기 도구 바인딩. `ChatAnthropic`으로 llm을 만들고, `ChatPromptTemplate`으로 system이랑 human 메시지를 정의하는데, 여기 보세요. `("placeholder", "{agent_scratchpad}")` 이 줄이 도구 호출 이력이 누적되는 자리예요. 세션 04에서 배운 스크래치패드 기억나시죠? 그게 여기 슬롯으로 들어와 있어요.

그리고 에이전트 조립. 이게 오늘의 하이라이트예요. `create_tool_calling_agent`로 agent를 만들고 `AgentExecutor`로 감싸요. 세션 02의 그 `while` 루프가 이 `AgentExecutor` 안으로 들어간 거예요. 그리고 `executor.invoke`에 질문을 넣어요. 질문이 "2024년 노벨 물리학상 수상자가 누구이고, 그 사람들이 받은 상금을 3으로 나누면 얼마야?"예요.

자 이제 진짜 보여줄 거예요. `verbose=True`로 돌리면 콘솔에 로그가 흐르는데, 세션 02 raw 루프의 다섯 단계가 한 줄 한 줄 그대로 찍혀요. 화면 로그를 같이 읽어볼게요.

```
> Entering new AgentExecutor chain...
Invoking: web_search with {'query': '2024 Nobel Prize physics winners'}
[{'snippet': '...수상자 John Hopfield, Geoffrey Hinton ... 상금 1,100만 SEK...'}]
Invoking: calculator with {'expression': '11000000 / 3'}
{'result': 3666666.67}
2024년 노벨 물리학상은 ... 상금을 3으로 나누면 약 3,666,667 SEK입니다.
> Finished chain.
```

보세요. 첫 번째 `Invoking: web_search` 줄, 이게 ①LLM 호출이랑 ②파싱이랑 ③실행이에요. LLM이 검색하기로 결정하고, 인자를 파싱하고, 실제로 도구를 부른 거죠. 그 아래 스니펫 줄, 수상자가 John Hopfield랑 Geoffrey Hinton이고 상금이 1,100만 SEK라는 결과가 스크래치패드에 ④ 주입된 거예요. 그다음 두 번째 `Invoking: calculator`, 이게 ⑤ 반복이에요. 다시 ①로 돌아가서 이번엔 계산기를 부른 거죠. 식이 `11000000 / 3`이에요. 결과가 3666666.67로 ④ 주입되고요. 마지막 줄, 도구 호출이 없으니까 종료. "상금을 3으로 나누면 약 3,666,667 SEK입니다." 자연어 답이 나왔어요.

여기서 꼭 짚을 게 있어요. `while True`는 사라진 게 아니에요. 이 로그 안에서 돌고 있어요. 화면에 세션 02랑 세션 06 대응표 보시면, `while True`는 AgentExecutor가 내부에서 반복하는 거고, `client.chat`은 llm 더하기 도구 바인딩, `parse_tool_call`은 프레임워크가 자동 파싱, `TOOLS[name]`은 tools 리스트 자동 디스패치, `messages.append`는 `agent_scratchpad`에 자동 누적, 종료 조건은 도구 호출이 없으면 자동 종료. 한 줄 한 줄 대응돼요. 이걸 칠판에 꼭 그려서 보여주세요.

💬 예상 질문 — "LangChain 쓰면 루프를 안 짜도 된다, 그러니까 루프가 없어진 거 아니에요?" 아니에요. 이게 제일 흔한 오해예요. 루프는 AgentExecutor 내부로 옮겨갔을 뿐 여전히 돌아요. 방금 verbose 로그에서 ①부터 ⑤까지 다 봤잖아요. 세션 02 코드를 옆에 띄워놓고 "이 줄이 저 안에 있다"고 매핑해 보여주면 이해가 확 빨라져요. 이 매핑이 오늘 세션의 핵심 학습 효과예요.

## [토론 · 15분] 추상화의 비용/이점, 프레임워크 vs raw

🎙️ 자 마지막으로 큰 그림을 그려볼게요. 추상화에는 비용과 이점이 둘 다 있어요. 화면 표를 같이 봐요.

초기 작성 속도는 raw가 느리고, glue를 직접 짜니까요, LangChain은 블록 조립이라 빨라요. 투명성이랑 디버깅은 거꾸로예요. raw는 전부 내 코드라 투명한데, LangChain은 내부 스택을 추적해야 해서 낮아요. 벤더 교체는 raw면 코드 수정이 필요하고 LangChain은 Model 한 줄 교체. 학습 곡선은 raw는 LLM API만 알면 되는데 LangChain은 프레임워크 개념이 추가되고요. 버전 변동성은 raw가 안정적이고 LangChain은 빠른 API 변화에 노출돼요. 세밀한 제어는 raw가 완전하고 LangChain은 추상이 가끔 가로막아요.

판단 기준을 정리하면요. raw가 유리한 경우는, 학습이나 이해가 목적일 때, 호출이 아주 단순할 때, 극단적인 성능이나 제어가 필요할 때, 의존성을 최소화하고 싶을 때. LangChain이 유리한 경우는, 여러 벤더랑 여러 도구랑 여러 단계를 빠르게 조합할 때, 표준 추적이나 평가 도구를 얹고 싶을 때, 팀이 공통 어휘를 쓰고 싶을 때.

핵심 메시지는 이거예요. 프레임워크는 생산성을 주고 투명성을 가져가요. 그런데 우리는 세션 02에서 루프를 직접 짜 봤기 때문에, LangChain의 AgentExecutor 안에서 "지금 ④ 결과 주입 단계구나"를 읽어낼 수 있어요. 그게 이 강의의 철학이에요.

토론 질문 몇 개 던질게요. 첫째, verbose 로그에서 세션 02 raw 루프의 ①부터 ⑤까지 각각 어디에서 찾을 수 있나요? 방금 같이 읽었죠. 둘째, `@tool`이 docstring을 도구 설명으로 쓴다면, docstring 품질이 에이전트 성능에 어떤 영향을 줄까요? 세션 03의 도구 설계 원칙과 어떻게 연결되나요? 셋째, LCEL의 파이프는 한 방향인데 우리 어시스턴트는 본질적으로 루프예요. 파이프만으로 표현 못 하는 게 뭐고, 그래서 AgentExecutor, 다음 주 LangGraph가 왜 필요할까요? 넷째, 벤더를 OpenAI에서 Claude로 바꿀 때 raw 버전이랑 LangChain 버전에서 각각 뭘 고쳐야 할까요? 다섯째, 여러분 실무 프로젝트에서 LangChain을 쓰는 게 투명성 손실보다 이득인 경계는 어디일까요?

💬 예상 질문 — "그럼 raw는 배울 필요 없었던 거 아닌가요?" 이게 진짜 중요한 포인트예요. 디버깅이랑 성능 튜닝이랑 예외 흐름은 결국 추상화 아래로 내려가야 해요. raw를 모르면 AgentExecutor가 멈췄을 때 손을 못 대요. "추상화 뒤를 알고 써라"가 이 강의의 척추예요.

🎙️ 오늘 정리하면, LangChain이 raw 루프의 어떤 glue를 추상화하는지, 핵심 추상 4종, LCEL의 파이프와 Runnable, 그리고 AgentExecutor 안에 세션 02의 while 루프가 그대로 돌고 있다는 걸 verbose 로그로 확인했어요. 다음 시간 세션 07에서는, LCEL의 한 방향 파이프로는 표현 못 했던 그 루프랑 조건분기를 정면으로 다뤄요. 같은 리서치 어시스턴트를 LangGraph 상태 그래프로 다시 그려볼게요. 수고하셨습니다.
