## [복습 · 5분] 세션 1 회상 — 루프와 4대 구성요소

🎙️ 자, 다시 만났습니다. 지난 세션 1에서 우리는 에이전트가 "루프를 도는 프로그램"이고 LLM은 그 루프의 두뇌, 즉 정책일 뿐이라고 했죠. 그리고 4대 구성요소 Reasoning·Tools·Memory·Planning도 봤어요. 잠깐 떠올려볼게요. 관찰하고, 사고하고, 행동하는 걸 정지 조건까지 반복하는 게 루프였죠.

오늘은 그중에서도 에이전트의 심장인 **Tools**, 정확히는 Tool Use 혹은 Function Calling을 해부합니다. 이 회차를 마치면 다섯 가지를 할 수 있어요. 모델은 함수를 실행하지 않고 "호출 의도"만 낸다는 실제 메커니즘을 정확히 설명하기, 도구 스키마를 모델이 잘 쓰도록 설계하기, 선택·실행·결과 주입 사이클을 메시지 수준에서 추적하기, raw API만으로 에이전트 루프를 `while`로 직접 구현하기, 그리고 정지 조건·무한루프 방지·에러를 도구 결과로 되돌리는 견고화 기법 적용하기.

그리고 오늘의 핵심 메시지 하나를 먼저 못 박을게요. "프레임워크, 즉 LangChain이나 LangGraph는 이 `while` 루프를 감싼 것일 뿐이다." 이거 오늘 내내 반복할 거예요.

## [개념강의 ① · 12분] Function Calling 메커니즘 — 모델은 실행하지 않는다

🎙️ 자, 가장 흔한 오해부터 깨고 시작할게요. LLM에 도구를 "붙여도" 모델이 코드를 직접 돌리는 게 아니에요. 모델은 그저 "이 함수를 이 인자로 부르고 싶다"는 구조화된 의도, 즉 tool call을 출력할 뿐이에요. 실제 실행은 우리, 클라이언트 코드의 책임이고, 그 실행 결과를 다시 모델에게 넣어줘야 합니다.

화면의 시퀀스 다이어그램을 같이 따라가볼게요. 우리 코드가 1번에서 tools 스키마와 메시지를 LLM에 보냅니다. LLM이 2번에서 tool_call, 즉 함수 이름과 인자를 반환하고 멈춰요. 3번에서 우리가 진짜 함수, web_search나 calculator를 실행합니다. 4번에서 그 결과를 tool 메시지로 LLM에 보내요. 그러면 5번에서 LLM이 다음 tool_call을 내거나 최종 답변을 줍니다.

쉽게 말하면 이런 거예요. 모델은 식당에서 주문서를 적는 손님이에요. "스테이크 미디엄으로 주세요"라고 주문서에 적는 것까지가 모델의 일이고, 실제로 고기를 굽는 건 주방, 즉 우리 코드예요. 손님이 직접 불 앞에 서지 않죠.

여기서 결정적 통찰이 나와요. 모델과 실행 사이엔 **사람이 만든 경계**가 있어요. 그래서 우리는 권한을 통제하고, 인자를 검증하고, 에러를 가공해서 되돌릴 수 있습니다. 그리고 "에이전트 루프"란 방금 본 1번부터 5번까지를 정지 조건까지 반복하는 거예요.

💬 이게 첫 번째 흔한 오해예요. "모델이 함수를 실행한다"는 거. 절대 아니에요. 모델은 호출 의도만 내고 멈춥니다. 실행은 우리 코드. 이 경계가 바로 권한 통제, 검증, 에러 가공이 일어나는 지점이에요. 수강생 대다수가 여기서 처음 "아하" 합니다.

## [개념강의 ② · 13분] 도구 스키마(JSON Schema) 설계

🎙️ 자, 그럼 모델이 도구를 언제 어떻게 부를지는 뭐가 결정할까요? 거의 전적으로 **스키마와 설명문**에 달려 있어요. 스키마는 모델에게 주는 API 문서이자 프롬프트입니다.

화면에 본 과정 공통 표준 도구 정의 두 개가 있어요. 첫째 web_search, description이 "주어진 검색어로 웹을 검색해 상위 결과 스니펫을 반환한다. 수상자·뉴스·사실 등 모델이 모르는 정보가 필요할 때 사용"이라고 돼 있고, 파라미터는 query 문자열 하나, required예요. 둘째 calculator, description이 "수식 문자열을 계산해 결과를 반환한다. 추측하지 말고 반드시 이 도구로 계산"이고, 파라미터는 expression 문자열 하나예요. 보세요, description에 "언제 써야 하는지"가 들어 있죠. 이게 핵심이에요.

화면 체크리스트 표를 볼게요. 이름은 `do_it`이나 `tool1` 같은 나쁜 예 대신 `web_search`, `calculator`처럼 동사 더하기 목적으로. description은 "검색함" 대신 언제 써야 하는지까지. 파라미터 수는 한 도구에 10개씩 말고 모델이 채우기 쉬운 최소 인자로. 타입과 제약은 자유 문자열 대신 enum, required, 포맷을 명시. 모호성은 두 도구 역할이 겹치지 않게 경계를 명확히.

원칙은 이거예요. 스키마는 "주니어 개발자에게 함수 쓰는 법을 알려준다"는 마음으로 쓰세요. 모델이 헷갈리면 90%는 description이 부실한 탓이에요. 모델 탓이 아닙니다.

화면의 BEFORE/AFTER 예시를 꼭 보여주세요. 같은 web_search인데 BEFORE는 description이 그냥 "검색한다"예요. 무엇을, 언제 쓰는지 전혀 없죠. AFTER는 "수상자·뉴스·최신 사실 등 모델이 모르는 정보가 필요할 때 사용"이에요. 호출 패턴 비교표를 보면, BEFORE는 언제 쓸지 몰라서 과소호출하거나 엉뚱하게 호출하는데, AFTER는 "내가 모르는 사실"이라는 트리거가 명확해서 제때 호출해요. 인자 품질도 BEFORE는 막연한 검색어인데 AFTER는 구체적 키워드로 채울 단서가 생기죠.

쉽게 말하면 description은 코드 주석이 아니라 모델이 읽는 프롬프트의 일부예요. 신입에게 "알아서 검색해"라고 하면 헤매지만, "네가 모르는 최신 사실이 필요할 때 이걸로 검색해"라고 하면 정확히 움직이는 거랑 같아요.

💬 두 번째 흔한 오해가 여기예요. "도구가 안 불리는 건 모델이 멍청해서"라는 거. 대개 description이나 스키마 부실이 원인이에요. 모델이 도구를 안 부른다고 느끼면 모델 탓하기 전에 description부터 의심하세요.

## [개념강의 ③ · 12분] 선택 → 실행 → 결과 주입 사이클 (메시지 흐름)

🎙️ 자, 이제 메커니즘과 스키마를 봤으니 실제로 메시지가 어떻게 흐르는지 볼게요. 여기서 핵심은 **대화 메시지 배열이 계속 자라난다**는 거예요. 각 턴이 다음 턴의 컨텍스트가 됩니다.

화면 흐름도를 같이 읽을게요. 처음 messages에는 system 메시지와 user 메시지, 즉 "노벨 물리학상 수상자와 상금을 3으로 나눈 값" 질문이 들어 있어요. ①에서 tools를 포함해 LLM을 호출하면, ②에서 모델이 assistant 메시지로 web_search를 부르겠다는 tool_calls를 내요. ③에서 우리가 실행해 결과를 얻고, ④에서 그 결과를 role이 tool인 메시지로 배열에 append합니다. 스니펫에 "상금 1,100만 SEK"가 들어오죠. ⑤에서 늘어난 messages로 다시 LLM을 호출하고 반복해요. 도구가 더 필요 없으면 tool_calls 없는 최종 assistant 메시지가 나오고 종료됩니다.

화면 표에 메시지 role별로 누가 만드는지 정리돼 있어요. system은 개발자가, 에이전트 정체성과 규칙. user는 사용자가, 목표와 질문. tool_calls가 든 assistant는 **모델**이, 어떤 도구를 어떤 인자로 부를지. role이 tool인 메시지는 **우리 코드**가, 도구 실행 결과 또는 에러 메시지. content가 든 assistant는 모델이, 도구가 끝났을 때의 최종 답.

쉽게 말하면 이 messages 배열은 점점 길어지는 **카톡 단톡방** 같은 거예요. 누가 무슨 말을 했는지 다 쌓이고, 다음 사람이 그 전체 대화를 보고 말하죠. 그리고 세션 1에서 말한 Memory, 그게 거창한 게 아니라 바로 이 messages 배열의 누적이 1차 형태예요.

💬 예상 질문. "도구 결과가 엄청 길면요? 검색 본문이 수천 토큰이면?" 좋은 질문이에요. messages가 계속 누적되니 컨텍스트가 폭발할 수 있죠. 요약하거나, 잘라내거나, 메모리를 분리하는 방법이 있는데, 이건 토론 질문으로 같이 다뤄볼 거예요.

## [개념강의 ④ · 13분] raw API로 에이전트 루프 직접 구현 (`while` 의사코드)

🎙️ 자, 드디어 오늘의 하이라이트예요. 프레임워크 없이 맨손으로 에이전트 루프를 짜봅시다. 데모 파일 `demos/01_raw_agent_loop.py`가 정확히 이 구조로 web_search와 calculator를 구현해요.

화면 의사코드를 한 줄씩 읽을게요. TOOLS 딕셔너리에 이름과 실제 함수를 매핑해둬요. run_agent 함수는 user_goal과 max_steps를 받는데, 기본값이 6이에요. demo-task-spec의 MAX_TURNS가 6이죠. messages는 system과 user로 시작합니다. 그다음 `for step in range(max_steps)` 루프, 이 상한이 바로 무한루프 방지예요. ①에서 모델에 선택을 요청하고, ②에서 어시스턴트 턴을 messages에 누적해요. ③에서 정지 조건을 체크하는데, tool_calls가 없으면 최종 답변을 반환합니다. tool_calls가 있으면 ④에서 요청된 도구를 하나씩 실행하는데, 인자를 json.loads로 파싱하고, try 안에서 함수를 부르고, 모르는 도구면 에러 문자열을 줘요. ⑤에서 예외가 나도 죽이지 않고 에러를 결과로 만들어요. ⑥에서 그 결과를 role이 tool인 메시지로 append해서 다음 루프의 컨텍스트로 넣어요. 그리고 루프가 ①로 돌아갑니다. ⑦에서 만약 max_steps에 도달하면 부분 결과로 비상 정지해요.

화면 아래 플로우차트로 한 장에 정리하면, step 시작에서 LLM 호출, tool_calls 있나 분기, 없으면 최종 답변 반환, 있으면 도구를 try/except로 실행, 결과 append, step이 max보다 작으면 다시 LLM 호출, 아니면 강제 종료. 이게 전부예요.

쉽게 말하면 이 루프는 "심부름 보내고, 결과 받아 적고, 더 시킬 게 있나 보고, 없으면 보고받고 끝" 하는 비서 관리 사이클이에요. 일곱 줄짜리 사이클이 심장입니다.

그리고 핵심 메시지를 다시 못 박을게요. LangChain의 `AgentExecutor`, LangGraph의 `create_react_agent`, 이게 본질적으로 이 `while` 루프를 감싼 거예요. 상태관리·재시도·관측가능성·분기를 더 줬을 뿐, 심장은 방금 본 일곱 줄짜리 사이클입니다. 프레임워크가 마법이 아니라는 걸 확인하는 게 오늘의 목적이에요.

💬 그래서 자주 나오는 질문이 "그럼 프레임워크는 왜 쓰나요?"예요. 심장인 `while` 루프는 동일하고, 프레임워크는 상태관리·재시도·스트리밍·관측가능성, 즉 tracing, 멀티에이전트 분기를 얹어줘요. 오늘의 목표는 프레임워크를 깐 뒤에도 안에서 무슨 일이 벌어지는지 아는 거예요. 그래야 디버깅이 됩니다.

## [개념강의 ⑤ · 8분] 정지 조건 / 무한루프 방지 / 에러 처리

🎙️ 자, 루프를 짰으면 이제 **스스로 멈출 줄 알아야** 프로덕션에 올릴 수 있어요. 자율 루프가 안 멈추면 그건 사고예요.

먼저 정지 조건. 화면 표를 보면 네 가지예요. tool_calls 없는 응답이면 모델이 "이제 답할 준비됨"으로 판단한 정상 종료, max_steps 도달이면 안전 상한, 예산 초과, 즉 토큰·시간·비용이면 운영 가드레일, 그리고 명시적 종료 도구 final_answer로 종료를 강제하는 설계도 있어요.

다음 무한루프 방지. 반드시 max_steps 상한을 두세요, 아까 의사코드의 for문이죠. 같은 tool_call, 즉 이름과 인자가 똑같은 호출이 반복되면 감지해서 경고를 주입하거나 강제 종료하고요. N스텝 동안 새 정보가 안 들어오는 진전 없음도 감지해서 중단해요. 모델이 헷갈려 빙빙 도는 패턴은 보통 스키마나 시스템 프롬프트가 부실하다는 신호예요.

쉽게 말하면 자율주행차에 브레이크와 제한속도가 없으면 안 되는 거랑 같아요. max_steps가 제한속도, 반복 감지가 "어, 같은 데 계속 도네?" 하는 경고등이에요.

그리고 가장 중요한 견고화, 에러를 "도구 결과"로 되돌리기예요. 도구가 실패해도 예외를 던져 루프를 죽이지 말고, 에러 문자열을 tool 결과로 모델에게 돌려주세요. 그러면 모델이 인자를 고쳐 재시도하거나 다른 도구로 우회할 수 있어요, 자기수정이죠. 화면 예시를 보면 calculator에 "11000000 / "라는 잘못된 식을 넣어 예외가 나도, 죽이지 말고 "ERROR: SyntaxError: invalid syntax"를 tool 결과로 주입해요. 그러면 모델이 관찰하고 스스로 "11000000 / 3"으로 교정해서 3666666.67을 얻어요.

💬 경고 하나, 이건 글로벌 규칙과도 일치해요. 빈 except로 에러를 삼키면 모델은 실패를 모른 채 잘못된 답을 냅니다. 최소한 에러 메시지를 도구 결과로 주입하고 로그를 남기세요. Silent failure 금지예요. 토론 때 "그럼 죽여야 마땅한 에러도 있을까?"도 같이 생각해봅시다.

## [데모 · 10분] 리서치 어시스턴트 한 사이클 trace

🎙️ 자, 그럼 방금 짠 `while` 루프가 실제로 어떤 메시지 배열을 만들어내는지 trace로 볼게요. 시나리오는 세션 1과 동일해요. "2024년 노벨 물리학상 수상자가 누구이고, 그 상금을 3으로 나누면 얼마야?" 도구는 web_search와 calculator, 검색은 mock 고정 결과, 상금은 mock 값 1,100만 SEK예요. 각 step이 LLM 1회 호출이에요.

화면 trace를 같이 읽을게요. step 1, system과 user만 있는 messages로 LLM을 호출하면, assistant가 web_search를 부르겠다고 tool_calls를 내요. 실행하면 스니펫에 "상금 1,100만 SEK"가 들어오고, 그걸 role이 tool인 메시지로 append합니다. step 2, 그 tool 결과가 더해진 messages로 다시 호출하면, 이번엔 calculator로 "11000000 / 3"을 부르겠다고 해요. 실행하면 result 3666666.67이 나오고 또 append. step 3, 정지예요. 다시 호출하니 assistant가 content로 "수상자는 ...이며, 상금 1,100만 SEK를 3으로 나누면 약 3,666,667 SEK입니다"라고 답하고, tool_calls가 없으니 정지 조건 충족, 루프 종료, 반환.

강조할 포인트가 핵심이에요. step 수, 여기선 3인데, 이게 코드에 없어요. 모델이 관찰을 보며 동적으로 결정한 거예요, 자율성과 루프. step 1에서 2로 넘어갈 때, 검색 스니펫에서 상금을 읽고 나서야 계산식을 만들 수 있었죠. 결과 주입이 다음 선택을 좌우한다는 거예요. 그리고 만약 step 2에서 calculator가 실패했다면? 아까 본 대로 에러를 주입해서 다음 step에서 모델이 식을 고쳐 재시도해요. 이 전체가 앞서 본 `while` 일곱 줄에서 나옵니다. 프레임워크는 이걸 감싼 포장이라는 점, 한 번 더 못 박을게요.

화면 관찰 표로 정리하면, 동적 step 수의 증거는 코드엔 max_steps만 있고 실제 3스텝은 모델이 결정했다는 것, 결과가 다음 선택을 좌우한 증거는 검색 스니펫을 관찰한 뒤에야 계산식이 나왔다는 것, 정지 조건은 step3에서 tool_calls가 사라졌다는 것, 견고화 여지는 도구 실패 시 에러 주입으로 자기수정이 가능하다는 것이에요.

## [토론 + 예고 · 7분] 토론 질문과 다음 회차

🎙️ 자, 마무리로 토론 질문 몇 개 던질게요. 첫째, web_search의 description을 어떻게 바꾸면 불필요한 검색을 줄일 수 있을까요? 반대로 과소호출은 어떻게 막죠? 둘째, 도구 결과가 수천 토큰으로 매우 길 때 messages 누적이 컨텍스트를 폭파시키는데, 요약·잘라내기·메모리 분리 중 어떻게 다룰까요? 셋째, max_steps를 너무 작게 또는 너무 크게 잡으면 각각 어떤 실패가 나고, 여러분 작업의 적정값은 뭘까요? 넷째, 에러를 예외로 죽이기와 도구 결과로 주입하기의 트레이드오프, 그리고 죽여야 마땅한 에러도 있을까요? 다섯째, 이 `while` 루프를 직접 짤 수 있다면 왜 굳이 LangChain이나 LangGraph를 쓸까요?

오늘 정리하면, 모델은 함수를 실행하지 않고 호출 의도만 낸다, 결과를 메시지로 다시 주입해 루프를 잇는다, 정지 조건과 MAX_TURNS로 무한 루프를 막는다, 도구 실패를 예외로 죽이지 말고 결과로 되돌려 자기수정을 유도한다, 좋은 description이 호출 품질을 좌우한다. 이렇게 다섯 개예요.

다음 세션 3은 추론과 계획 패턴이에요. 오늘 만든 이 `while` 루프 "안에서 다음에 무엇을 할지 결정하는 머리"를 다룹니다. CoT, ReAct, Plan-and-Execute, Reflection을 같은 리서치 과제에 적용해 trace를 비교할 거예요. 프레임워크로의 이식은 세션 6부터 7에서 합니다. 수고하셨어요.
