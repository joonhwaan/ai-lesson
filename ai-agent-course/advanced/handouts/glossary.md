# AI 에이전트 개발 마스터 코스 — 용어집(Glossary)

> 10개 세션에 반복 등장하는 핵심 용어를 **주제별로 묶어** 정리했다. 각 항목은 "쉬운 정의 → 왜 중요한가 → 주의점" 순으로 읽으면 된다. 끝의 `(S#)`는 그 개념을 처음/주로 다루는 세션 번호.
> 공통 예제는 **리서치 어시스턴트**(도구: `web_search` · `calculator` · `fetch_url` · `summarize` · `cite`)다.
> 알파벳 순 색인이 필요하면 브라우저 검색(Ctrl+F)으로 영문 표제어를 찾으면 된다.

---

## 1. 에이전트의 기초 — "에이전트란 무엇인가"

- **Agentic Loop(에이전틱 루프)** — 에이전트의 심장. **관찰(Observe) → 추론(Think) → 행동(Act)** 을 목표를 이룰 때까지, 혹은 종료조건에 걸릴 때까지 반복하는 제어 흐름이다. 사람이 문제를 풀 때 "상황을 보고 → 생각하고 → 행동하고 → 결과를 다시 보는" 과정을 코드로 옮긴 것. 이 루프가 있느냐 없느냐가 단순 "LLM 호출 한 번"과 "에이전트"를 가른다. (S1)
- **Autonomy(자율성)** — 다음에 무엇을 할지를 **사람이 정하는가, 모델이 정하는가**의 정도. 낮으면 개발자가 흐름을 코드로 다 정해둔 것(Workflow)이고, 높으면 모델이 매 순간 스스로 다음 행동을 고르는 것(Agent)이다. 실제 제품은 이 둘 사이 스펙트럼 어딘가에 놓인다 — 자율성이 높을수록 유연하지만 예측·통제가 어려워진다. (S1)
- **Workflow(워크플로우)** — LLM을 언제 어떻게 호출할지가 **코드로 미리 고정된** 결정적 파이프라인. "이 단계 다음엔 반드시 저 단계"처럼 개발자가 흐름을 통제한다. 자율성 스펙트럼에서 Agent의 반대편 — 예측 가능하고 디버깅이 쉬운 대신, 예상 못 한 상황에 스스로 대응하진 못한다. (S1)
- **Harness(하네스)** — 그냥 모델(LLM)을 **"에이전트로 동작하게 만드는 모든 코드"** 를 통칭한다: 루프, 컨텍스트를 조립하는 부분, 도구 라우팅, 서브에이전트 호출, 안전·관측 훅 등. 핵심 격언은 =="모델이 아니라 하네스가 제품이다"==. 같은 모델이라도 하네스 설계에 따라 결과 품질이 완전히 달라진다. 세션 2의 while 루프가 가장 작고 원초적인 하네스다. (S10)
- **MAX_TURNS** — 에이전트 루프가 **최대 몇 번까지 반복할지**의 상한값. 모델이 도구 호출과 재시도를 무한히 반복하며 비용을 태우는 사고를 막는 가장 기본적인 안전장치다. (S2)
- **Stop Condition(정지 조건)** — 루프를 **언제 멈출지**를 정하는 규칙. 보통 "모델이 더는 도구를 부르지 않고 최종 답 텍스트를 냈을 때" 멈추고, 그 전에 MAX_TURNS를 넘기면 강제 종료한다. 종료조건이 허술하면 에이전트가 끝없이 맴돈다. (S2)

## 2. 도구 사용 — "모델이 바깥 세상과 연결되는 법"

- **Function Calling(함수 호출 / Tool Use)** — 모델이 직접 계산하거나 검색하는 대신, **"어떤 도구를 어떤 인자로 부를지"를 구조화된 JSON으로 출력**하면 하네스가 실제로 그 도구를 실행하고 결과를 다시 모델에 돌려주는 메커니즘. 흐름은 Tool Schema(도구 사용법 알려주기) → 모델의 호출 요청(JSON) → 도구 실행 → Tool Result(결과 주입)의 사이클이다. 에이전트가 세상과 상호작용하는 가장 근본적인 동작. (S2)
- **Tool Schema(도구 스키마)** — 도구의 **이름·설명·입력 파라미터**를 모델이 이해할 수 있게 적어둔 계약서(JSON Schema). 모델은 이 설명만 보고 도구를 언제 어떻게 쓸지 판단하므로 =="description이 곧 프롬프트"== 다 — 설명이 애매하면 모델이 도구를 엉뚱하게 쓰거나 안 쓴다. (S2)
- **Tool Result(도구 결과)** — 도구를 실행한 결과를 모델에게 되돌려주는 메시지. 성공 결과뿐 아니라 **실패·에러도 모델이 읽을 수 있는 형태로 줘야** 모델이 "아 실패했구나, 다시 해보자"라고 스스로 고칠 수 있다. 에러를 조용히 삼키면 에이전트는 무엇이 잘못됐는지 모른 채 진행한다. (S2)
- **Grounding(그라운딩)** — 모델이 상상해서 답하지 않고, **도구가 가져온 실제 데이터에 답을 근거시키는 것**. 환각(hallucination)을 줄이는 핵심 원리 — "네 기억으로 답하지 말고, 검색해서 나온 이 문서를 근거로 답하라"가 그라운딩이다. (S2)
- **MCP(Model Context Protocol)** — 에이전트를 외부 도구·데이터 소스에 연결하는 **표준 규격**. 도구마다 제각각 연동 코드를 짜는 대신, MCP를 따르면 표준화된 방식으로 여러 도구를 꽂아 쓸 수 있다 — USB 표준처럼 "한 번 규격을 맞추면 아무거나 꽂힌다"는 아이디어. (S2·S6)

## 3. 추론 전략 — "모델이 더 똑똑하게 생각하게 만드는 법"

- **Chain-of-Thought(CoT, 생각의 사슬)** — 곧바로 답을 내지 말고 **중간 추론 과정을 글로 펼치게** 해서 정확도를 높이는 기법. 사람도 암산보다 종이에 풀어쓸 때 정답률이 오르듯, 모델도 생각을 토큰으로 "외재화"하면 복잡한 문제를 더 잘 푼다. (S3)
- **ReAct(Reason + Act, 추론+행동)** — **추론(Thought) → 행동(Action) → 관찰(Observation)** 을 번갈아 반복하는 패러다임. "생각하고 → 도구를 쓰고 → 결과를 보고 → 다시 생각한다." 검색이나 도구에 의존하는 과제에서 특히 강하다. 사실상 CoT에 도구 사용을 결합한 것. (S1·S3)
- **Self-Consistency(자기 일관성)** — 같은 질문을 **여러 번 다른 방식으로 풀게 한 뒤 다수결로 답을 고르는** 기법. 한 번의 추론이 틀릴 수 있으니, 여러 경로가 같은 답에 수렴하면 그게 정답일 가능성이 높다는 발상. 답이 하나로 수렴하는 문제(수학 등)에 잘 맞는다. (S3)
- **Reflection / Reflexion(자기 성찰)** — 모델이 **자기 출력을 스스로 비평하고 다시 시도하는** 루프. Reflexion은 한발 더 나아가 "이번에 왜 실패했는지"를 언어로 정리해 메모리에 쌓아, 다음 시도에서 같은 실수를 피하게 한다. (S3)
- **Tree-of-Thoughts(ToT, 생각의 나무)** — 추론을 **여러 갈래로 뻗은 나무처럼 탐색**하면서 각 갈래를 평가하고, 막히면 되돌아가(백트래킹) 다른 길을 시도하는 기법. 매우 강력하지만 갈래마다 모델을 호출하므로 비용이 곱셈으로 불어난다. (S3)
- **Plan-and-Execute(계획 후 실행)** — **먼저 전체 계획을 세우는 부분(planner)** 과 **한 단계씩 실행하는 부분(executor)** 을 분리한 구조. 매 스텝 즉흥적으로 정하지 않으니 일관성이 높고 토큰도 아끼지만, 처음 세운 계획이 틀리면 그대로 어긋난 채 진행되는 약점이 있다. (S3)
- **Scratchpad(스크래치패드)** — 모델이 추론 과정이나 진행 메모를 **컨텍스트 안에 적어두고 참고하는 임시 작업 공간**. 사람이 문제를 풀며 여백에 끄적이는 메모장과 같다. (S3·S4)

## 4. 메모리 & 컨텍스트 — "유한한 기억을 어떻게 관리할 것인가"

- **Context Window(컨텍스트 윈도우)** — 모델이 **한 번에 볼 수 있는 토큰(글자 조각)의 최대량**. 사람의 "작업 기억"처럼 유한하고, 길수록 비용·지연이 커진다. 대화가 길어지면 여기에 다 안 들어가므로 메모리 전략이 필요해지는 근본 이유이며, 컨텍스트 엔지니어링에서는 이를 ==예산==으로 본다. (S4·S10)
- **Memory(메모리, 단기/장기)** — **단기 기억** = 지금 세션의 대화·scratchpad(컨텍스트 안), **장기 기억** = 세션이 끝나도 남는 외부 저장소(벡터DB 등). 모델 자체는 대화가 끝나면 다 잊으므로, "기억한다"는 것은 사실 =="필요할 때 관련 정보를 다시 컨텍스트에 넣어주는" 엔지니어링== 이다. (S4)
- **Lost in the Middle(가운데서 길 잃기)** — 긴 컨텍스트에서 **중간쯤에 놓인 정보를 모델이 잘 활용하지 못하는** 현상. 사람이 긴 목록에서 처음과 끝만 기억하는 것과 비슷하다. 그래서 정말 중요한 정보는 컨텍스트의 앞이나 뒤에 배치한다. (S4)
- **Summarization Buffer(요약 메모리)** — 오래된 대화를 **요약으로 압축해 보관**하는 메모리 방식. 공간은 아끼지만 요약 과정에서 숫자·인용 같은 세부가 누락될 위험이 있어, 핵심 사실은 요약과 별도로 원본 보존이 필요하다. (S4)
- **Compaction(컴팩션)** — 대화가 너무 길어지면 **오래된 이력을 요약으로 압축하고 최근 맥락만 원본으로 남기는** 것. 손실 압축이라 요약하면서 정보가 사라질 수 있으므로, 절대 잃으면 안 되는 핵심 사실은 따로 state에 보존한다. (S10)
- **Context Engineering(컨텍스트 엔지니어링)** — 유한한 컨텍스트 윈도우에 **매 턴 무엇을 넣고 뺄지를 설계하는 일**. 네 개의 레버 — **쓰기(밖에 저장)·선택(필요한 것만 불러오기)·압축(요약)·격리(서브에이전트로 분리)** — 로 토큰 예산을 배분한다. "프롬프트 잘 쓰기"의 다음 단계라 볼 수 있다. (S10)
- **Context Failure(컨텍스트 실패 모드)** — 컨텍스트가 오염돼 성능이 나빠지는 네 가지 방식: **중독(Poisoning, 틀린 정보가 눌러앉음)·산만(Distraction, 관련 없는 내용에 휩쓸림)·혼동(Confusion, 도구·정보가 뒤섞임)·충돌(Clash, 모순된 정보 공존)**. 증상으로 원인을 진단해 위 네 레버로 교정한다. (S10)
- **Token Budget(토큰 예산)** — 컨텍스트를 "최대한 꽉 채우자"가 아니라 **한정된 예산처럼 아껴 배분해야 한다**는 관점. 꽉 채우면 오히려 품질이 떨어지고 비용·지연만 오르므로, "필요한 최소한"만 넣는 게 원칙이다. (S10)

## 5. RAG & 검색 — "외부 지식을 끌어와 근거로 삼는 법"

- **RAG(Retrieval-Augmented Generation, 검색 증강 생성)** — 모델이 자기 기억만으로 답하지 않고, **관련 문서를 먼저 검색해 그 내용을 근거로 답을 생성**하는 방식. 최신 정보나 사내 문서처럼 모델이 학습하지 못한 지식을 다룰 때 필수이며, 에이전트 장기기억의 한 형태이기도 하다. 아래 청킹·임베딩·벡터DB·재랭킹 등이 모두 RAG를 구성하는 부품이다. (S4·S5)
- **Agentic RAG(에이전틱 RAG)** — 검색을 고정된 파이프라인이 아니라 **에이전트의 판단에 맡기는** 방식. "검색을 할지 말지, 질의를 어떻게 바꿀지, 몇 번 다시 검색할지"를 모델이 스스로 정한다. 대표 변형으로 self-RAG(가져온 근거가 충분한지 스스로 평가)와 corrective RAG(검색이 부실하면 감지해 다시 질의)가 있다. 정적 RAG보다 유연한 대신 비용·지연·무한루프 위험이 늘어 종료조건 관리가 중요하다. (S5)
- **Chunking(청킹)** — 긴 문서를 검색 단위인 **조각(청크)으로 쪼개는** 작업. 조각 크기와 겹침(오버랩)이 핵심 손잡이 — 너무 작게 쪼개면 맥락이 잘려나가고, 너무 크게 쪼개면 임베딩이 뭉개져 검색 정확도가 떨어진다. (S5)
- **Embedding(임베딩)** — 텍스트를 **의미를 담은 숫자 벡터(고차원 좌표)로 바꾸는** 것. 의미가 비슷한 문장은 벡터 공간에서 서로 가까이 위치해, "글자가 아니라 뜻으로" 검색할 수 있게 된다. 색인할 때와 질의할 때 **반드시 같은 임베딩 모델**을 써야 좌표계가 맞는다. (S5)
- **Vector DB(벡터DB) / ANN** — 임베딩 벡터를 저장하고 **의미가 가까운 이웃을 빠르게 찾아주는(근사 최근접 이웃, ANN)** 데이터베이스. 수백만 벡터를 일일이 비교하면 느리므로 IVF·HNSW 같은 색인 구조로 "거의 정확하지만 훨씬 빠른" 검색을 한다. 장기기억의 전형적인 구현체. (S5)
- **Hybrid Search(하이브리드 검색)** — **키워드 검색(BM25)** 과 **벡터(의미) 검색** 을 함께 써서 정확도를 높이는 것. 고유명사·코드·제품번호처럼 정확한 글자가 중요한 건 키워드가, 의역·동의어처럼 뜻이 중요한 건 벡터가 강하므로 둘을 합치면 서로의 약점을 보완한다. (S5)
- **Re-ranking(재랭킹)** — 1차로 빠르게(벡터) 후보를 많이 가져온 뒤, **정밀한 모델(cross-encoder 등)로 다시 순위를 매겨 진짜 상위만 남기는** 2단계 전략. 1차 검색은 "빠뜨리지 않기(recall)"를, 재랭킹은 "정확히 골라내기(precision)"를 담당한다. (S5)
- **Metadata Filtering(메타데이터 필터링)** — 청크에 붙여둔 **구조화된 정보(날짜·문서종류·작성자·권한 등)로 검색 범위를 미리 좁히는** 것. 특히 접근 권한(멀티테넌시)은 프롬프트로 "보지 마"라고 부탁하는 게 아니라 **검색 단계에서 아예 걸러내야** 안전하다. (S5)

## 6. 프레임워크 — LangChain (S6)

- **AgentExecutor** — 도구 호출 루프를 대신 돌려주는 LangChain 런타임. 세션 2에서 직접 짠 `while` 루프를 **프레임워크가 감싸 제공하는 것**이라 보면 된다. (S6)
- **LCEL(LangChain Expression Language)** — `|` (파이프) 기호로 컴포넌트를 이어붙이는 **선언적 표현 언어**. 유닉스 파이프처럼 "A의 출력을 B의 입력으로" 연결한다. 단, 한 방향 흐름만 표현할 수 있어 되돌아가는 루프는 표현하지 못한다(그래서 LangGraph가 등장). (S6)
- **Runnable** — LangChain의 모든 컴포넌트가 공유하는 **공통 실행 인터페이스**(`invoke`/`stream`/`batch`). 부품마다 사용법이 제각각이 아니라 규격이 통일돼 있어, 레고 블록처럼 자유롭게 조합할 수 있다. (S6)
- **Output Parser(출력 파서)** — 모델이 뱉은 **자유 텍스트를 구조화된 형태(JSON·Pydantic 객체 등)로 변환·검증**하는 컴포넌트. "모델 출력을 프로그램이 바로 쓸 수 있는 데이터로 다듬는" 마지막 단계. (S6)

## 7. 프레임워크 — LangGraph (S7)

- **State Graph(상태 그래프)** — 공유 상태(state)를 두고 **노드(작업)와 엣지(연결)로 흐름을 그림처럼 정의**하는 LangGraph의 실행 모델. 세션 2의 while 루프를 눈에 보이는 그래프로 "펼쳐" 1급 시민으로 다루는 것. (S7)
- **Conditional Edge(조건부 엣지)** — 현재 상태값에 따라 **다음에 어느 노드로 갈지 갈라지는 동적 분기**. 노드 안에 `if`를 숨기는 대신 분기 자체를 그래프 구조로 드러내, 흐름을 한눈에 보고 디버깅할 수 있게 한다. (S7)
- **Reducer(리듀서)** — 여러 노드가 반환한 부분 결과를 **전체 상태에 어떻게 합칠지 정하는 규칙**(예: 리스트에 이어붙이기). 특히 여러 worker가 동시에 상태를 쓸 때 서로 덮어써 충돌하는 것을 막아준다. (S7·S8)
- **Checkpointer(체크포인터)** — 그래프의 상태를 **저장해두는 영속화 계층**. 덕분에 중단했다가 재개하기, 사람 승인 대기(HITL), "과거 시점으로 되돌려 다시 실행"(time-travel 디버깅)이 가능해진다. (S7)
- **ToolNode** — LangGraph에서 **도구 실행을 담당하는 미리 만들어진 노드**. 세션 2 루프의 "도구를 실제로 부르는 부분"을 그래프의 정식 노드로 승격시킨 것. (S7)
- **Human-in-the-loop(HITL, 사람 개입)** — 되돌릴 수 없거나 위험한 동작(결제·삭제·전송 등) 직전에 **사람의 승인을 받도록 멈추는 지점**. LangGraph에서는 `interrupt`로 구현한다. 완전 자율과 완전 수동 사이의 안전한 타협점. (S7·S9)

## 8. 멀티 에이전트 — "여러 에이전트를 조율하는 법" (S8)

- **Supervisor(Orchestrator, 감독자)** — 큰 작업을 **잘게 쪼개 부하 에이전트에게 나눠주고 결과를 다시 합치는** 중앙 조정 에이전트. 지휘가 명확하고 통제가 쉽지만, 모든 것이 그를 거치므로 병목이자 단일 장애점(SPOF)이 되기 쉽다. (S8)
- **Network / Swarm(네트워크/스웜)** — 중앙 조율자 없이 **에이전트들이 서로 직접 일을 넘기는** 구조. 유연하고 확장성이 좋지만, 서로 끝없이 떠넘기는 무한 위임 루프에 빠질 위험이 있다. (S8)
- **Hierarchical(계층형)** — 감독자 위에 또 감독자를 두는 **여러 층으로 된 조직도 같은** 오케스트레이션. 큰 조직을 팀→부서→본부로 나누듯, 복잡한 문제를 층층이 분담시킨다. (S8)
- **Handoff(핸드오프)** — 한 에이전트가 다른 에이전트에게 **"제어권 + 지금까지의 맥락"을 함께 넘기는** 행위. 콜센터에서 상담원이 "담당자 바꿔드릴게요" 하며 통화 내용까지 인계하는 것과 같다. (S8)
- **Sub-agent(서브에이전트)** — 메인 대화를 어지럽히지 않도록, 일을 위임받아 **자기만의 깨끗한 컨텍스트에서 처리하고 ==결론만== 돌려주는** 에이전트. 진짜 가치는 "일꾼이 여러 명"이라는 데 있지 않고 =="컨텍스트 격리"== — 지저분한 중간 과정을 메인에서 분리하는 데 있다. (S8·S10)
- **SPOF(Single Point of Failure, 단일 장애점)** — **그 하나가 멈추면 시스템 전체가 멈추는 지점**. 멀티 에이전트에서 중앙 Supervisor가 대표적인 예다. 이중화·폴백(대체 경로)·타임아웃으로 위험을 완화한다. (S8)

## 9. 평가 · 안전 · 운영 — "프로덕션에서 믿고 쓰는 법" (S9)

- **LLM-as-a-Judge(LLM 심판)** — 사람이 일일이 채점하는 대신 **다른 LLM에게 채점 기준(루브릭)을 주고 출력을 평가하게** 하는 기법. 빠르고 저렴하지만, 심판 모델이 긴 답·특정 위치·자기가 쓴 답을 편애하는 편향이 있어 주의해야 한다. (S9)
- **Trajectory(궤적) 평가** — 최종 답만 보는 게 아니라 **거기 도달하기까지 밟은 경로(도구 호출 순서·인자 등)를 평가**하는 것. 답은 맞았어도 도구를 쓸데없이 많이 불렀다면 효율·비용 문제를 이걸로 잡아낸다. (S9)
- **Tracing / Observability(추적/관측가능성)** — 모든 LLM·도구 호출을 **기록하고 시각화해** 무엇이 언제 왜 일어났는지 들여다볼 수 있게 하는 것(LangSmith 등). 블랙박스 같은 에이전트를 디버깅·개선하려면 필수 — "볼 수 없으면 고칠 수 없다." (S9)
- **Guardrail(가드레일)** — 에이전트의 **입력·출력·행동을 제약하는 안전·정책 장치**(권한 최소화, 위험 동작 승인 게이트, 타임아웃 등). 도로의 가드레일처럼 "정상 범위를 벗어나지 못하게" 막는 울타리. (S9)
- **Prompt Injection(프롬프트 주입)** — 에이전트가 읽어온 **외부 데이터(웹페이지·문서 등)에 몰래 심어둔 지시를, 모델이 진짜 명령으로 착각해 따르는 공격**. 핵심 방어 원칙은 =="외부에서 가져온 데이터는 신뢰하지 않는다"== — 데이터를 명령이 아닌 데이터로만 취급하기. (S9)
