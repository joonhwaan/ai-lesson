## [프레이밍 · 8분] 혼자 다 읽지 마라 — 위임과 격리

🎙️ 자, 이 트랙의 하이라이트 시간이에요. 오늘은 에이전트 ==여러 대==를 부리는 법을 배웁니다. 멀티 에이전트라고 하면 다들 "동시에 돌리니까 빠르겠네!"부터 떠올리시는데, 오늘 제가 가장 강조하고 싶은 건 그게 아니에요. **잘 나누고, 반드시 합쳐서 검증하는 것** — 이게 핵심이에요.

왜냐하면 병렬은 공짜가 아니거든요. 잘못 나누면 ==마지막 에이전트가 앞 에이전트 작업을 통째로 덮어써요.== 그것도 조용히요. 그래서 오늘 시간의 절반은 "속도"가 아니라 "어떻게 나누고, 끝나고 뭘 검증하나"에 쓸 거예요.

비유하면, 공사 현장에 인부 다섯 명을 한꺼번에 투입했는데 다섯 명이 같은 벽을 동시에 칠하면? 마지막 사람 페인트만 남고 앞 네 명 일은 사라져요. 인부를 늘리는 게 능사가 아니라, ==누가 어느 벽을 맡을지 나누는 게== 능사예요.

🎙️ 오늘은 크게 다섯 덩어리예요. 서브에이전트가 왜 "격리"인지, 병렬 탐색은 언제 하는지, 그리고 오늘의 핵심인 배치 전략, 역할 분담, 마지막으로 통합 검증 체크리스트. 시작할게요.

## [핵심① · 16분] 서브에이전트 = 컨텍스트 격리

🎙️ 첫째, 서브에이전트가 뭐냐. 메인 에이전트가 ==별도의 깨끗한 컨텍스트를 가진 보조 에이전트==한테 일을 맡기는 거예요. Claude Code에선 Task 도구로 부르죠. 그런데 여기서 사람들이 오해하는 게 있어요. 서브에이전트의 1번 가치는 "병렬"이 아니라 ==**컨텍스트 격리**==예요.

생각해 보세요. 무거운 탐색, 그러니까 파일 수십 개를 훑어서 "이 기능이 어디서 어떻게 도나"를 알아내는 일을 메인에서 직접 하면, 그 읽은 파일 내용이 ==전부 메인 컨텍스트에 쌓여요.== 근데 내가 정작 필요한 건 결론 한 단락이잖아요? 나머지 99%가 컨텍스트를 채워서, 지난 세션에서 배운 그 "오염·포화"를 앞당겨요.

🎙️ 화면 다이어그램을 보세요. 메인은 깨끗한 컨텍스트를 유지하면서, 서브에이전트 A랑 B한테 탐색을 위임해요. 서브들은 각자 격리된 컨텍스트에서 파일 50개씩 읽어요. 그런데 메인한테 돌려주는 건? ==결론만요.== "인증은 auth/middleware.js의 verifyToken을 거치고, 토큰은 jwt.sign으로 발급된다" 이 한 줄만 받아요. 파일 더미는 서브 컨텍스트에 쌓였다가 그냥 버려져요.

지난 세션의 clear랑 compact가 "내 컨텍스트를 관리하는" 거였다면, 서브에이전트는 =="남한테 짐을 떼어내는"== 관리예요. 한 단계 위의 컨텍스트 운용 기술이에요.

💬 예상 질문: "그럼 서브한테 시키면 그 탐색 결과를 메인이 못 보는 거 아니에요?" → 결론은 봐요. 파일 원문을 안 볼 뿐이죠. 그게 핵심이에요 — 판단에 필요한 결론만 가져오고, 짐은 떼어내는 거예요. 더 깊이 들어가고 싶으면 못 다시 물어보면 되고요.

## [핵심② · 14분] 병렬 탐색 패턴 — 언제 위임, 언제 직접

🎙️ 둘째예요. 서브에이전트는 ==동시에 여러 개== 띄울 수 있어요. 서로 다른 영역을 병렬로 조사시키면, 하나씩 순차로 읽는 것보다 빨리 전체 그림이 모여요.

화면 예시를 보세요. 결제 버그를 추적한다고 쳐요. 메인이 세 영역을 동시에 서브로 던져요. 서브 A는 프런트 결제 폼이 어떤 API를 어떤 형식으로 부르나, 서브 B는 백엔드 라우트가 뭘 검증하고 뭘 반환하나, 서브 C는 DB 스키마랑 트랜잭션. 세 결론이 한꺼번에 모이면, 메인이 "아 여기 불일치네"를 바로 짚죠.

🎙️ 근데 중요한 건 ==언제 위임하고 언제 직접 하느냐==예요. 화면 표를 보세요. 넓은 범위를 훑어야 하거나 독립된 여러 영역을 동시에 봐야 하면 위임. 반대로 한두 파일만 보면 되는 작은 확인은 ==그냥 메인에서 직접== 하세요. 위임에는 띄우고 회수하는 비용이 들거든요. 작은 일까지 매번 위임하면 오히려 느려져요.

그리고 하나 더 — 위임은 ==조사==고, 결정은 ==메인==이에요. 서브한테 탐색과 수집을 맡기되, "그래서 어떻게 고칠까"라는 판단이랑 실제 편집은 메인이 해요. 물론 서브한테 구현까지 시킬 수도 있는데, 그건 다음 섹션 배치 전략 얘기고요. 탐색 위임이랑 구현 위임은 구분해서 생각하세요.

💬 예상 질문: "그냥 다 병렬로 띄우면 제일 빠르지 않아요?" → 아니에요. 작은 확인은 위임 오버헤드가 더 크고, 독립적이지 않은 작업을 병렬로 띄우면 다음 섹션에서 볼 충돌이 나요. 병렬은 ==독립적이고 무거운== 조사에만 쓰는 거예요.

## [핵심③ · 24분] 멀티 에이전트 배치 전략 (오늘의 핵심)

🎙️ 자, 오늘의 진짜 핵심이에요. 탐색을 넘어서 ==여러 에이전트가 동시에 코드를 짓게== 하면 속도가 확 붙어요. 근데 여기서부터 ==충돌==이라는 새 위험이 생겨요. 병렬 구현의 성패는 거의 ==배치를 어떻게 나누느냐==에서 결정돼요.

먼저 절대 규칙 하나. **같은 파일을 두 에이전트가 동시에 수정하면 안 돼요.** 화면 경고를 보세요. 두 에이전트가 같은 파일을 각자 고치면, ==마지막에 저장한 애 결과만 남고 앞 작업은 통째로 덮어써져요.== 조용히 사라지니까 더 위험하죠. 이게 멀티 에이전트 1번 사고 유형이에요.

🎙️ 그래서 배치의 제1원칙은 ==수정 파일 기준 그룹핑==이에요. 같은 파일을 건드리는 작업은 ==반드시 같은 에이전트에== 몰아넣어요. 화면 표를 보세요. index.js, database.js, App.jsx, 전역 CSS 같은 공유 파일은 한 에이전트에 몰거나, 병렬로 각자 짓고 ==메인에서 통합==하세요. DB 테이블을 여럿이 추가하면 database.js가 충돌하니까, 한 에이전트가 모든 테이블을 만들거나 각자 ALTER TABLE로 분리하고요.

🎙️ 여기서 꼭 짚을 게 하나 더. **npm install은 에이전트 실행 전에 미리 끝내세요.** 여러 에이전트가 동시에 install을 돌리면 lock 파일이 충돌해서 설치가 깨져요. 의존성 설치는 병렬 시작 전에 메인에서 한 번에 끝내 두세요. 마이그레이션이나 빌드처럼 전역 상태를 바꾸는 작업도 마찬가지로 직렬화하고요.

🎙️ 다음, 의존성이에요. 배치는 "동시에 할 수 있는 걸" 묶는 일이에요. ==서로 의존하면 병렬이 아니라 순차==예요. 화면 예시처럼, 거래 기능이 리뷰 데이터에 의존하면, 리뷰가 미완성인데 거래를 동시에 짜면 깨져요. 리뷰 먼저 끝내고 검증한 다음에 거래를 시작해야죠.

라우트 순서도 같은 함정이에요. 화면 보세요 — `/products/:id`라는 와일드카드가 `/products/suggest`보다 먼저 등록되면, suggest가 id로 먹혀버려요. ==구체 라우트를 와일드카드보다 먼저== 등록해야 해요.

🎙️ 마지막으로 에이전트 프롬프트 작성 원칙. 이게 진짜 중요해요. ==서브에이전트는 이전 대화 맥락을 몰라요. 백지 상태예요.== 세션 1에서 "에이전트는 아까 그거를 모른다"고 했죠? 그 원칙이 여기서 결정적이 돼요. 화면 표를 보세요. 구체적 파일 경로랑 줄 번호, 기존 코드의 현재 상태, API 응답 형식을 ==필드명까지==, 기존 패턴 참조, 그리고 "Read로 먼저 읽고 Edit으로 수정"까지 명시하세요. 안 그러면 파일도 안 읽고 작업하는 경우가 생겨요.

특히 응답 형식은 ==필드명까지 못 박으세요.== 병렬 에이전트는 서로의 코드를 못 봐요. "검색 API 만들어줘"가 아니라 "GET /products/search가 products랑 total을 반환, 기존 라우트와 같은 에러 처리"처럼 계약을 적어야, 프런트 담당이랑 백엔드 담당 결과가 맞물려요. 이 한 줄이 뒤에 나올 통합 검증 부담을 절반으로 줄여줘요.

💬 예상 질문: "에이전트끼리 서로 대화하면서 맞추면 안 돼요?" → 기본적으로 각 에이전트는 자기 일만 보고 전체 맥락을 몰라요. 그래서 ==계약을 미리 명시하는 게== 제일 확실하고, 그래도 어긋나는 건 마지막 통합 검증에서 잡는 거예요. 서로 알아서 맞추겠지, 하고 기대하면 silent fail로 이어져요.

## [핵심④ · 10분] 역할 분담 — 구현·리뷰·테스트

🎙️ 넷째예요. 병렬을 "영역별"로만 나누는 게 아니라 ==역할별==로도 나눌 수 있어요. 한 작업을 단계가 다른 에이전트들이 릴레이하는 거죠. 화면 표 보세요. 구현 에이전트는 계획대로 코드를 짜고, 코드리뷰 에이전트는 버그랑 엣지케이스랑 ==빈 catch==를 점검하고, 테스트 에이전트는 테스트를 짜고 돌려서 통과를 확인해요.

🎙️ 여기서 포인트는, 역할 분담도 ==격리의 이점==을 쓴다는 거예요. 리뷰랑 테스트 에이전트는 구현 컨텍스트에 안 물든 ==신선한 눈==으로 봐요. 자기가 짠 코드는 자기 가정을 의심하기 어렵잖아요. 근데 별도 컨텍스트의 리뷰어는 "이 가정이 맞나?"를 새로 물어요. 단, 구현 → 리뷰 → 테스트는 의존 관계니까 보통 ==순차==로 굴려요. 앞 섹션 의존성 얘기 그대로예요.

## [핵심⑤ · 12분] 통합 검증 체크리스트 + silent failure 방지

🎙️ 다섯째, 그리고 오늘 절대 빼면 안 되는 부분이에요. 병렬 구현이 끝났다고 끝이 아니에요. ==각 에이전트는 자기 담당 파일만 보고 전체 맥락을 몰라요.== 그래서 병렬 후엔 ==반드시== 메인에서 교차 검증을 해야 해요. 이걸 건너뛰면 "각자는 맞는데 합치면 안 도는" 상황이 나요.

화면 체크리스트 여섯 개를 같이 볼게요. ① API 인터페이스 — 서버 응답 필드랑 클라이언트 기대값이 일치하나. 서버가 messages를 주는데 클라가 res.data.room을 기대하면? ==silent fail==이에요. ② 공유 파일이 정상 병합됐나. ③ import나 require가 빠지지 않았나. ④ 라우트 순서 — 와일드카드가 구체 라우트보다 뒤인가. ⑤ DB 스키마 — 테이블이랑 컬럼이 다 생성됐나. 그리고 ⑥ 브라우저 E2E.

🎙️ 이 ⑥번을 진짜 강조하고 싶어요. **API 테스트만으로는 불충분해요.** API가 200을 주고 단위 테스트가 다 녹색이어도, ==실제 화면에선 안 보이거나 안 눌리는== 경우가 흔해요. 응답 구조 불일치, CSS 레이아웃, 렌더링 조건 같은 건 ==브라우저에서 눈으로== 봐야만 잡혀요. 병렬 구현의 마지막 관문은 언제나 E2E예요. 자동 테스트가 초록불이라고 안심하지 마세요.

🎙️ 그리고 silent failure 얘기. 화면 경고처럼 ==빈 catch(e) {} 는 금지==예요. 빈 catch는 에러를 조용히 삼켜서 문제를 숨겨요. 멀티 에이전트에선 더 치명적이에요 — 한 에이전트가 만든 불일치를 다른 쪽 빈 catch가 덮어버리면, ==아무 에러 없이 기능만 안 되는== 최악의 디버깅 상황이 돼요. 최소한 console.error라도 넣어서 흔적을 남기세요. silent fail의 주범이 대개 그 ①번 API 응답 구조 불일치라서, 에러가 보여야 추적이 되거든요.

🎙️ 화면 아래 미니 시나리오를 보세요. 상품 리뷰 기능 하나를 3개 에이전트로 나눠요. 사전에 메인이 npm install이랑 DB 마이그레이션을 직렬로 끝내고요. 백엔드 에이전트는 reviews.js, 프런트 에이전트는 ProductDetail이랑 ReviewList. 근데 database.js는 공유 파일이니까 ==메인이 단독으로== reviews 테이블을 추가해서 충돌을 피해요. 추천 기능은 리뷰에 의존하니까 리뷰 끝나고 순차로. 그리고 마지막에 메인이 체크리스트 여섯 개를 다 돌려요. 특히 avg냐 average냐 같은 필드명 오타까지 확인하고, 브라우저에서 리뷰 작성부터 평균 평점 표시까지 눈으로 확인하는 걸로 마무리예요.

💬 예상 질문: "검증을 매번 여섯 개 다 돌리면 번거롭지 않아요?" → 병렬로 아낀 시간을 여기서 조금 쓰는 거예요. 그리고 ①번 API 계약을 프롬프트에 잘 박아두면 검증 부담이 확 줄어요. 배치를 잘하면 통합이 쉬워지는, 앞뒤가 연결된 얘기예요.

## [실습·정리 · 6분] 한 기능을 3개 에이전트로

🎙️ 마무리 실습이에요. 작은 기능 하나를 골라서, 오늘 배운 대로 ==배치 → 병렬 → 통합== 세 박자로 돌려보세요. 수정 파일로 그룹핑하고, 공유 파일은 메인이 잡고, 의존성은 순차로 풀고, 끝나면 체크리스트 여섯 개로 마무리. 한 번 손으로 해보면 "아 병렬만 보면 안 되는구나"가 몸에 와요.

한 문장으로 정리할게요 — **멀티 에이전트의 힘은 병렬이 아니라, 잘 나누고 반드시 합치는 데서 나와요.** 무거운 탐색은 서브에이전트에 위임해 결론만 회수하고, 구현은 수정 파일로 그룹핑해서 충돌을 막고, 의존성은 순차로 풀고, 끝나면 통합 검증 체크리스트로 마무리한다. 시간을 아끼는 건 병렬이지만, ==결과를 지키는 건 배치와 통합 검증==이에요.

다음 시간엔 에이전트 동작 자체를 내 손에 맞추는 법을 배울게요. 항상 적용되는 프로젝트 규칙, 특정 이벤트에 자동 실행되는 훅, 외부 도구를 끌어오는 MCP까지요. 오늘 배운 멀티 에이전트 규칙들 — 빈 catch 금지나 패턴 일관성 같은 거 — 을 ==규칙으로 굳혀서== 모든 에이전트가 따르게 만드는 법도 거기서 이어집니다. 수고하셨습니다. 질문 받을게요.
