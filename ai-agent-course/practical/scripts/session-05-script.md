## [프레이밍 · 8분] 도구를 내 프로젝트에 길들이는 3층

🎙️ 다섯 번째 시간이에요. 지금까지 루프, 명령, 스킬, 멀티 에이전트를 배웠죠? 다 도구를 *쓰는 법*이었어요. 오늘은 한 발 더 나가서, 도구를 **내 프로젝트에 맞게 길들이는** 법을 배웁니다.

생각해 보세요. 매번 대화 시작할 때마다 "우린 에러를 Toast로 처리해", "빈 catch 쓰지 마", "빌드는 build.py로 해" 이런 걸 반복해서 말하고 있다면 낭비죠. 또 "커밋 전엔 테스트 돌려"라고 했는데 에이전트가 까먹고 그냥 넘어가면 곤란하고요. 그리고 에이전트가 우리 DB나 브라우저에 직접 접근했으면 좋겠는데 방법이 없다면 답답하죠.

🎙️ 이 세 가지 답답함이 정확히 오늘의 세 층이에요. **규칙, 훅, MCP.** 한 줄로 정리하면 — 규칙은 "무엇을 알아야 하나", 그러니까 맥락이에요. 훅은 "무엇이 자동으로 일어나야 하나", 동작이고요. MCP는 "무엇과 연결되나", 도구예요. 셋은 역할이 안 겹쳐요. 일을 어디에 둘지 헷갈리면 이 한 줄로 가르면 돼요. 그 위에 권한 모드로 안전선까지 긋고 마무리할게요.

## [핵심① · 20분] CLAUDE.md 규칙 — 항상 주입

🎙️ 첫 번째 층, 규칙이에요. 입문 레슨 12에서 에이전트 맞춤 설정 배웠죠? 그 핵심이 `CLAUDE.md`예요. 프로젝트 루트에, 또는 전역으로 홈의 `.claude` 폴더에 이 파일을 두면, **매 대화 시작할 때 자동으로 컨텍스트에 주입**돼요. 매번 관례를 반복해 말할 필요가 없어지는 거죠.

화면 예시를 보세요. 코딩 스타일로 "에러는 Toast로 통일, alert 금지", 금지사항으로 "빈 catch 금지", 빌드 절차로 ".md 수정 후 build.py 실행" 이런 걸 불릿으로 적어두는 거예요. 그러면 에이전트가 매 대화에서 이걸 알고 시작해요.

🎙️ 위치는 두 군데예요. 홈의 `.claude/CLAUDE.md`는 전역이라 내 모든 프로젝트에 적용돼요. 내 개인 습관을 적죠. 프로젝트 루트의 `CLAUDE.md`는 이 레포에만 적용되고 git에 커밋해서 팀과 공유해요. 이 프로젝트만의 관례랑 아키텍처를 적고요.

🎙️ 여기서 제일 중요한 주의사항. **장황하게 쓰지 마세요.** 이 파일은 매 대화에 통째로 주입돼요. 길수록 컨텍스트를 먹고 핵심이 묻혀요. 소설처럼 쓰지 말고, 자주 어기는 관례랑 금지사항, 빌드 절차만 짧게. 세션 2에서 배운 `#`으로 한 줄씩 쌓아가는 것도 좋은 습관이에요. 책상 앞에 붙이는 메모지지 두꺼운 매뉴얼이 아니에요.

💬 예상 질문: "CLAUDE.md에 다 적어두면 에이전트가 무조건 지키나요?" → 아니에요. 주입은 되지만 100% 지켜지는 건 아니에요. 규칙은 '권유'예요. 반드시 매번 강제돼야 하는 건, 바로 다음에 배울 훅으로 넘겨야 해요.

## [핵심② · 22분] 훅 — 이벤트에 자동 실행

🎙️ 두 번째 층, 훅이에요. 방금 그 질문이 자연스럽게 여기로 이어져요. 훅은 **특정 이벤트가 일어날 때 내가 정한 명령을 자동으로 실행**하는 장치예요. `settings.json`에 설정하고요.

대표적인 쓰임 세 가지. 첫째, 도구 실행 전후예요. 예를 들어 파일을 편집하고 나면 자동으로 포맷터를 돌린다, 위험한 명령은 차단한다. 둘째, 응답 완료 시점이에요. 끝나면 알림음이나 데스크톱 토스트로 "다 됐어" 하고 알려주는 거죠. 셋째, 커밋이나 작업 마무리 때 테스트랑 린트를 자동으로 돌리는 거예요.

🎙️ 화면의 `settings.json` 예시를 보세요. 편집이 일어나면, 그러니까 Edit이나 Write 도구가 쓰이면, 그 후에 prettier로 포맷하라는 거예요. 단, 이 필드 이름이랑 이벤트 이름은 대표 예시예요. 버전마다 다를 수 있어요.

🎙️ 자, 오늘 가장 중요한 한 문장이에요. **항상 자동으로 일어나야 하는 동작은 메모리나 규칙이 아니라 훅으로 해야 실제로 실행돼요.** `CLAUDE.md`에 "편집하면 포맷해"라고 적어도 에이전트가 건너뛸 수 있어요. 하지만 훅은 이벤트가 나면 무조건 돌아요. 이게 '권유'랑 '강제'의 차이예요. 규칙은 권유, 훅은 강제. 이거 하나만 가져가셔도 오늘 성공이에요.

🎙️ 그런데 정확한 이벤트 이름이나 매처 문법은 버전마다 달라요. 세션 2에서 "명령 추측하지 말고 `/help`" 했던 거 기억하시죠? 똑같아요. 지어내지 말고 `/hooks`나 설정 UI에서 현재 지원되는 이벤트 목록을 보고 고르세요.

💬 예상 질문: "그럼 훅을 많이 걸수록 좋은 거 아니에요?" → 아니에요. 훅은 무조건 돈다는 게 양날의 검이에요. 훅 명령이 느리거나 실패하면 매 이벤트마다 발목을 잡아요. 전체 빌드 같은 무거운 작업을 빈번한 이벤트에 걸면 작업이 답답해져요. 가벼운 알림 같은 것부터 시작하시길 권해요.

## [핵심③ · 18분] MCP — 외부 도구 연결

🎙️ 세 번째 층, MCP예요. 입문 레슨 05에서 MCP를 "도구계의 USB"라고 배웠죠? 그 개념이 여기서 실전으로 와요. MCP는 Model Context Protocol의 약자인데, 에이전트랑 외부 도구·데이터 소스를 **표준 프로토콜**로 이어줘요. 한 번 붙여두면 에이전트가 필요할 때 그 도구를 알아서 호출하고요.

화면 표를 보세요. 뭘 붙이냐 — 브라우저 자동화로 실제 페이지를 열어 클릭하고 스크린샷 찍기, 데이터베이스로 스키마 조회하고 쿼리 실행, 이슈 트래커로 이슈 읽고 코멘트, 사내 위키나 검색 같은 외부 API. 이런 걸 다 붙일 수 있어요. 관리는 `/mcp`로 해요. 연결된 서버 목록이랑 상태를 보고 인증도 하고요.

🎙️ 여기서 "표준 프로토콜"이라는 게 진짜 핵심이에요. USB를 생각해 보세요. 한 번 규격을 맞추면 마우스든 키보드든 USB 메모리든 같은 구멍에 꽂잖아요. MCP도 똑같아요. 한 번 규격을 맞추면 어떤 MCP 서버든 같은 방식으로 붙어요. 도구마다 따로 통합 코드를 짤 필요가 없어요. 그래서 브라우저, DB, 이슈트래커를 전부 같은 손동작 `/mcp`로 관리하는 거예요.

💬 예상 질문: "아무 MCP 서버나 막 붙여도 되나요?" → 조심하셔야 해요. MCP 서버는 외부 시스템에 접근해요. DB에 쓰거나, 브라우저로 외부 사이트에 접속하거나. 그래서 신뢰할 수 있는 서버만 붙이고, 그게 뭘 할 수 있는지 확인한 뒤에 쓰세요. 특히 DB 쓰기나 결제처럼 되돌리기 어려운 동작은, 다음에 배울 권한 모드랑 같이 봐야 해요.

## [핵심④ · 14분] 권한 모드 & 설정 계층

🎙️ 네 번째예요. 지금까지 규칙으로 맥락 주고, 훅으로 동작 자동화하고, MCP로 외부 도구를 붙였어요. 그런데 이게 강력해질수록, 에이전트가 **무엇을 자동으로 해도 되는지** 선을 그어야 해요. 그게 권한 모드예요.

화면 표를 보세요. 크게 세 구분이에요. 첫째 읽기 전용 또는 플랜 모드 — 편집이나 실행은 안 하고 탐색이랑 계획만 해요. 세션 1에서 배운 플랜 모드가 여기죠. 큰 작업 전에 계획 검토할 때 써요. 둘째 승인 필요, 이게 보통 기본값이에요 — 편집하거나 셸 실행할 때 그때그때 승인을 받아요. 안전이랑 속도의 균형이죠. 셋째 자동 승인 — 승인 없이 진행해요. 신뢰된 격리 환경에서 반복 작업 속도를 높일 때요.

🎙️ 그리고 설정은 계층으로 쌓여요. 화면처럼 전역이 제일 넓은 기본값이고, 프로젝트 설정이 그걸 덮어쓰고, 로컬 설정이 또 그걸 덮어써요. 좁은 범위가 넓은 범위를 이기는 거예요. 그래서 팀 공통 규칙은 프로젝트에 두고 커밋하고, 민감한 개인 설정은 로컬에 둬서 커밋 안 되게 해요.

🎙️ 자동 승인 얘기를 좀 더 할게요. 빠르긴 한데, 되돌리기 어려운 동작 — 파일 삭제, 푸시, 외부 전송 — 까지 무방비로 실행될 수 있어요. 그래서 자동 승인은 **격리 환경이랑 한 쌍**이에요. 신뢰된 격리 환경에서, 무엇을 허용할지 좁게 명시해서 써요. 비가역 작업은 확인 먼저, 이 원칙이 여기 그대로 적용돼요. 집에 비유하면, 자동 승인은 모든 문을 다 열어두는 거예요. 안전한 내 방 안에서나 하는 거지, 길거리에서 하면 안 되죠.

💬 예상 질문: "어떤 명령은 허용이고 어떤 건 차단인지 꼬였어요." → 어느 계층에서 정의됐는지부터 보세요. 전역인지 프로젝트인지 로컬인지. `/permissions`로 현재 상태를 확인하고, 민감한 허용은 커밋 안 되는 로컬에 두면 돼요.

## [정리 · 8분] 과설정 경계 + 내 프로젝트 점검

🎙️ 마무리예요. 오늘 배운 규칙, 훅, MCP가 다 강력해서, 자칫 **과하게 깔기 쉬워요.** 그러면 오히려 느려지고 혼동돼요. 긴 `CLAUDE.md`는 컨텍스트를 먹고, 무거운 훅은 매 이벤트를 잡고, 안 쓰는 MCP 서버는 도구 목록만 어지럽혀요.

화면의 과설정 신호를 보세요. CLAUDE.md가 한 화면을 넘어가면 핵심이 묻힌 거예요. 훅 때문에 매 편집이 눈에 띄게 느려지면 떼야 하고요. `/mcp` 목록에 안 쓰는 서버가 쌓이거나, 권한 규칙이 너무 많아 뭐가 허용인지 모르겠으면 정리 신호예요. 처방은 간단해요. 자주 어기는 규칙만 남기고, 무거운 훅은 빈번한 이벤트에서 떼고, 안 쓰는 건 제거하고, 권한은 좁고 명확하게.

🎙️ 이거 세션 2에서 배운 "치트시트" 원칙이랑 똑같아요. 명령 다 외우지 말고 자주 쓸 다섯 개만 골랐던 거 기억하시죠? 커스터마이징도 똑같아요. 실제로 효과 본 것만 남겨요. "있으면 좋을 것 같아서" 깔린 설정이 가장 먼저 정리 대상이에요.

🎙️ 한 문장으로 정리할게요 — **커스터마이징은 도구를 내 프로젝트에 길들이는 3층이에요. 규칙은 항상 주입, 훅은 이벤트에 강제 실행, MCP는 외부 도구 연결.** 항상 일어나야 하는 동작은 규칙이 아니라 훅으로, 외부 연결은 MCP로, 그 위에 권한 모드랑 설정 계층으로 안전선을 긋되, 꼭 필요한 만큼만 깐다.

다음 시간엔 드디어 실전이에요. 세션 1부터 5까지 따로 배운 루프, 명령, 스킬, 멀티 에이전트, 커스터마이징을 한 작업에 다 엮어서, 실제 기능 하나를 처음부터 끝까지 완성해 볼게요. 오늘 깐 규칙이랑 훅이랑 MCP가 실전에서 어떻게 맞물리는지 직접 보실 거예요. 수고하셨습니다. 질문 받을게요.
